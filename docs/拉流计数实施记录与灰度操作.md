# 拉流计数实施记录与灰度操作

本文记录工作区实现与边界，原始问题、真值验收口径和分阶段要求见 [逐问题解决方案](./拉流与越线计数逐问题解决方案.md)。本地修改尚未部署，现场准确率尚未验收。

## 已实现

- FFmpeg 首次使用时以本地合成流探测帧同步参数，优先 `-fps_mode passthrough`，再试 `-vsync 0`；两个均失败时回退 OpenCV，失败缓存 300 秒后允许重试。RTSP 还会分别探测 FFmpeg/ffprobe 支持的 `-timeout` 或旧版 `-stimeout`。每路健康信息显示实际解码后端、源尺寸与输出尺寸。
- WVP 分页异常、缺页、重复条目、通道查询失败、在线状态未知与 AI 列表查询失败均不按空列表处理；独立设备继续同步，同进程的同步调用串行。点播失败按通道退避，默认上限 120 秒；这可减少连续失败请求，但实际恢复可能延后，需结合现场故障时长调整。名称及注册关系无法确认时保留 GB 身份与原管道，`wvp_sync_status` 标记 `registration_unconfirmed`，新通道仍受注册名单限制。该保护不能代替多后端实例间的协调或现场名单核验。
- 合并 Gitee 同事的 WVP 通道改名迁移：仅在通道和 AI 状态已确认、目标名称符合注册要求时处理；已运行的设备先确认点播可用和旧管道停妥，再原子校验身份及配置并迁移 Redis 键。冲突时不覆盖目标键，尽量恢复旧管道；保留改名前后名称日志，历史事件和小时桶不会自动迁移到新 ID。
- 设备接口保留长、短名称别名解析；若最长的归一化名称有多个匹配，拒绝猜测，避免把操作转发到错误设备。
- 配置接口与 AI 入口检查有限坐标、线/锚点、ROI 有效性及其与计数线的交集。无效配置不覆盖之前配置；历史 WVP 无效配置不自动启流。凹 ROI 的所有有效计数线段均参与判断，允许窄 ROI 两次外部观测之间的真实跨线；配置页面以绿色显示有效线段，旧客户端未确认多段 ROI 时不能启用。
- 跨线拒绝原因区分速度、有效线段、同轨迹重复、反向冷却和方向禁用；未知类别不再默认计为车辆。对当前允许类别仍维持原来的人车口径。Ultralytics 8.3/8.4 的 tracker 共用进程内单调 ID 源，重建或 reset 不回绕；返回轨迹时避免 float32 大整数舍入，空检测也推进状态。
- 计数器先生成候选，SQLite 在一个事务中保存事件、轨迹/配置证据和发送任务，成功后才推进内存去重状态。事件重试复用相同 ID；发送成功后保留本地 `event_journal`，而不是删除审计明细。证据包含流代次、线/ROI/方向配置与哈希、轨迹、类别、交点、确认时间、计数参数及本地时间来源。已有待发送队列在启动时迁入新表。
- 可选 `journal_v2` 协议将事件及证据写入 MySQL `traffic_event_ledger`，同一行代表已持久接收及待物化任务。v2 要求事件时间包含时区偏移，物化时转换为业务时区后归入日/小时；旧协议时间格式不变。独立物化任务按设备入账顺序调用 Redis 的事件 ID 幂等更新；相同 ID 与不同内容冲突。MySQL 提交后响应丢失或 Redis 成功后物化状态更新前退出均可重试。旧协议保留且仍为默认。
- 本地 watchdog 以约 5 秒间隔记录保守的处理缺口；进程异常退出后，从上一检查点到新代恢复期间记录可能缺口。`GET /devices/{device_id}/coverage` 查询本地记录；`/health` 显示处理状态、事件及缺口存储异常。缺口区间采用本机墙钟和检查点，不等于摄像机 PTS，不可视为精确断流起止。
- 帧的本机墙钟与单调时钟出现回退或明显跳变时，重置该路跟踪和计数状态，记录可能缺口，不根据跳变前后的两个点推断穿线。墙钟回退后缺口存储也可能出现时间倒退错误，会在健康状态中保留错误供排查。
- 提供只读配置扫描 `scripts/audit_counting_configs.py` 和本地事件到 MySQL/Redis 的只读对账 `scripts/reconcile_event_journal.py`；命令不读取或输出流 URL，不自动修改计数。

## 默认配置和试验开关

| 配置 | 默认 | 使用说明 |
|---|---|---|
| `INFER_ENGINES_PER_GPU` | `1` | `2` 为单卡双引擎试验，各引擎模型和各路 tracker 独立；固定 `INFER_SLOTS_PER_GPU` 按每卡总槽位分配，奇数向下取整，显存需实测。 |
| `DECODE_FPS_SAMPLING` | `interval` | `grid` 在 FFmpeg 内使用输入 PTS 分桶选帧，可能出现短时突发；无 PTS 时保留输入帧。输出 rawvideo 仍不携带源 PTS。 |
| `EVENT_DELIVERY_PROTOCOL` | `legacy` | `journal_v2` 需先启用并验证后端账本；只确认 MySQL 已接收，Redis 是否物化需另看账本状态。 |
| `EVENT_LEDGER_ENABLED` | `false` | 后端启用 v2 时还需 `MYSQL_ENABLED=true` 和可用 MySQL；表按需创建，持久化失败返回 503。 |
| `BUSINESS_TIMEZONE` | `Asia/Shanghai` | v2 归档时区；Compose 同时将 AI 与后端进程时区设为该值，修改前须确认历史桶及切换水位。 |
| `CLOCK_JUMP_TOLERANCE_S` | `2` | 墙钟和单调时钟增量相差超过该秒数时重置状态；不应设置为负数。 |
| `WVP_PLAY_RETRY_MAX_S` | `120` | 自动同步的单通道点播失败最大退避秒数；正常点播立即清除失败记录。 |

GPU Compose 保持原有 `INFER_BATCH_TIMEOUT_MS=80`、`DECODE_MAX_SHORT_SIDE=540`、单引擎及 legacy 事件协议。`configs/business_rules.yaml` 中的 `inference.imgsz=960`、`inference.decode_max_fps=8` 优先于同名环境默认值；比较 640/960 或 6/8 时须修改隔离试验配置并核对 `/health` 生效值。双引擎和 `grid` 不应仅凭 GPU 利用率启用，必须对同一标注视频比较误报、漏报、各路帧间隔、延迟、CPU 和显存。

### 1080P、CPU 已不构成主要瓶颈时的试验组合

现场报告 GPU 利用率不高、CPU 瓶颈基本解决后，[1080P 计数试验参数](../configs/1080p-count-accuracy-trial.env.example)保留为单引擎对照：`gpu_batch`、每卡 1 引擎、FP16、解码短边 540（1080P 源输出 960×540）、`imgsz=960`、采样上限 8 FPS、`grid` 选帧、组批等待 40 ms。已知单卡 T4 的资源读数后，优先对比双引擎候选及容量配置，详见[总方案](./AI系统问题汇总与优化方案.md)的 T4 试验参数。试验文件依赖当前工作区实现，不能假定旧部署版本支持所有开关；它不会自动覆盖现场环境。

在固定 25 FPS 的本地合成源上，`interval` 上限 8 时选出约 6.25 FPS，`grid` 约 8 FPS，均选择原始输入帧。`grid` 的短时间帧间隔可以变化，源 PTS 异常或缺失时行为也会不同；下游仍可能因处理跟不上而覆盖帧。因此不承诺实际处理帧率、GPU 利用率或计数精度随之提高。`40 ms` 可能降低等待，也可能让批次变小、吞吐下降。

1. 固定现场真实有效配置、32 路 1080P 输入、模型和标注视频；先记录基线，分 8、16、24、32 路逐级试验。单卡 T4 先单变量比较单/双引擎，再分别对比 `interval` 与 `grid`、80 ms 与 40 ms；本参数文件是单引擎且 `grid`、40 ms 均启用的对照组合。优先核查远景、夜间、拥挤遮挡、端点及零事件设备。
2. 通过原启动配置加载参数文件，核对当前 shell 没有同名变量覆盖；`configs/business_rules.yaml` 中确认 `inference.imgsz: 960` 和 `decode_max_fps: 8.0`。组批窗口及环境参数在引擎初始化时读取，变更须按现场流程重建 AI 容器；这会中断计数并重置内存跟踪状态，应记录缺口、保留事件队列。检查 `/health` 的当前推理尺寸、下一连接采样设置、`infer.mode` 和每个引擎的 `batch_timeout_ms`；检查 `/devices` 的实际 `decode_backend`、源/输出尺寸、处理 FPS 和最大处理间隔。若实际退回 OpenCV，`grid` 不生效。
3. 同源录像按设备、类别和方向逐事件匹配真值，比较误计、漏计；同时看各路有效 FPS、采样后覆盖丢帧、最大处理间隔、延迟、平均批次和 GPU 显存。原目标是每设备大部分完整 30 秒窗口达到 5 FPS，完整门槛以[总方案的上线验收标准](./AI系统问题汇总与优化方案.md)为准。仅提高采样帧数或 GPU 利用率不能作为通过依据；影子试验必须使用隔离的事件队列和统计库。
4. 单卡 T4 的双引擎候选为 `INFER_ENGINES_PER_GPU=2`，配合 `INFER_SLOTS_PER_GPU=0`、`INFER_CAPACITY=32` 和 `INFER_SLOTS_MAX=32`；满载时各 16 路，无额外接入槽位，先比较吞吐、丢帧、精度和显存。若远景小目标漏检明显，可单独试 `DECODE_MAX_SHORT_SIDE=720` 配合 YAML 的 `inference.imgsz=1280`（1080P 源输出 1280×720），比较远景召回是否抵消处理帧率下降。原方案 `imgsz=640` 与采样上限 6 的候选仍可做对照，但不作为当前准确率优先的首选。
5. 指标或真值下降时停止扩批，恢复试验前实际配置；对默认配置的回退通常是 `DECODE_FPS_SAMPLING=interval`、`INFER_BATCH_TIMEOUT_MS=80`、`INFER_ENGINES_PER_GPU=1`，但现场覆盖值可能不同。回退需重建 AI 容器并记录空窗，不能清空 outbox 或直接修改统计值。

在已部署当前工作区代码的隔离环境或经安排的维护窗口，可以用下面命令加载组合。命令会**重建当前编排中的 AI 服务并中断计数**；它不会在同一台机器上创建独立的影子实例。

```bash
docker compose --env-file .env.gpu --env-file configs/1080p-count-accuracy-trial.env.example \
  -f docker-compose.gpu.yml up -d --no-deps --force-recreate ai
```

当前 `scripts/start_all_gpu.sh` 只加载 `.env.gpu`，不会读取试验文件；以后重新运行原脚本可能恢复为 `.env.gpu` 中的值。若试验通过且准备长期采用，应在现场维护的配置中明确写入已选值，并保留原值及回退记录。

## 扫描、灰度与回退

1. 使用现网的只读 Redis 连接，在后端容器执行 `python -m scripts.audit_counting_configs`。它读取容器已有 `REDIS_URL`，以 JSON 输出设备、GB 映射、配置状态和多段数；返回码 1 表示发现无效配置。先按报告核对历史设备线、锚点、ROI 和方向，修复后再启用。已有名称匹配异常需要人工确认，不会自动删除。
2. 先在隔离环境验证所有设备对应的 1080P 源、FFmpeg 后端、配置预览和事件投递。依照原方案收集夜间、遮挡、端点、六个零事件设备及其他典型场景的视频和双人复核真值，逐事件核对；没有样本的设备标记未验收。
3. 在隔离账本试用 v2：后端同时设置 `MYSQL_ENABLED=true` 和 `EVENT_LEDGER_ENABLED=true`，检查 `/api/events/capabilities` 的 `ledger=journal-v2` 和 `/api/events/ledger-status` 的 `ready`、物化任务、积压；然后才在 AI 侧设置 `EVENT_DELIVERY_PROTOCOL=journal_v2`。正式切换前确保设备只有一个生产者，排空旧队列并记录切换水位，保留 SQLite 与 MySQL 备份。影子计数必须写入隔离的 Redis/MySQL，不能与正式生产者共同累计。
4. 后端容器已只读挂载 AI 的 `event-outbox` 卷与脚本，可执行 `python -m scripts.reconcile_event_journal --sqlite /app/event-outbox/events.sqlite3`。脚本使用后端已有的 MySQL 和 Redis 连接环境变量，按 SQLite 与 MySQL 各自水位检查本地事件 ID、内容及 Redis 去重指纹，返回差异与样本 ID；加 `--device 设备ID --since-received 'YYYY-MM-DD HH:MM:SS'` 可列出指定设备和接收时间之后的后端独有事件候选。其他生产者和切换前事件可能产生合法候选，不能直接认定丢失。在线只读 SQLite 若受 WAL 文件权限影响，先通过 SQLite backup API 生成一致快照后再核对；不同数据库并非同一时刻快照，差异应复查。
5. 对协议、采样和引擎分别灰度：先单设备，再多设备；记录设备健康、缺口、队列最老年龄、`/api/events/ledger-status`、小时归档隔离状态和真值指标。v2 回退前停止新生产、排空队列并按 ID 核对已接收与已物化水位，再切换 `EVENT_DELIVERY_PROTOCOL=legacy`；保留两侧账本，不能删除未发送或未物化事件。单引擎回退设 `INFER_ENGINES_PER_GPU=1`，采样回退设 `DECODE_FPS_SAMPLING=interval`，并按部署流程重建相关服务。
6. SQLite 事件审计和 MySQL 账本当前不会自动清理，必须监控容量、做一致性备份，并在建立归档、保留期限和恢复演练后再制定清理策略。Redis 去重记录同样需要容量与持久化监控。

## 尚未完成或依赖现场的事项

- 本地事务可保证**已提交候选**和投递任务共同保存；重启时当前 tracker 重新建轨，未恢复进程退出前的完整视觉状态，也不能补出事务提交前或未观察到的目标。跨重连 ID 切换、遮挡和录像补算仍需现场真值验证。
- MySQL v2 与逐设备双向 ID 候选对账已实现，但跨生产者归属证明、权威账本驱动的 Redis 重建、小时桶完整性证明、自动补偿/冲正、业务区域初值和历史 legacy 事件补录尚未实现；不能把本地脚本结果当作完整业务账已对平。
- 断流缺口依赖 watchdog 和本机时钟；未对接 NVR、精确源 PTS、冻结画面检测或离线回放补算。旧协议保留无偏移的本地时间，历史桶时间来源需核查。画面长期不变但仍有帧时可能无法识别为冻结。
- 现有方向、防抖阈值、端点规则、轨迹缝合、分类和跨镜头业务口径未凭空改写；多段 ROI、参数、类别及线路没有完整逐设备版本回退和审计人员字段。未做真实 GPU 单/双引擎压测，也未实现推理和跟踪拆分为新的并行队列。
- 隔离合成测试和 CPU 权重加载不能证明现场的视频计数精度。须按原方案完成逐设备、逐类别、逐方向的真值对照以及 72 小时覆盖验证，之后才能评价准确率和部署效果。

## 隔离链路验证记录

使用本地隔离 RTSP 服务推送 1920×1080 合成移动公交车画面；实际 FFmpeg 输出 960×540，CPU 加载项目 YOLO 权重和 BoT-SORT，处理 12 帧并生成 1 条 `VehicleEnter`，事件已写入独立 SQLite。该试验仅证明一条合成链路可用，未验证现场摄像头、GPU 并发、真实车辆或人员的准确率。

与 Gitee 同事的改名、别名、轨迹去重及 FFmpeg 兼容修改合并后，隔离 Redis/MySQL 完整测试为 94 项及 20 个子测试通过；另分别在 Ultralytics 8.3 和 8.4 验证跟踪器重建、reset 和大整数 ID。未进行真实 T4 或现场视频计数验收。

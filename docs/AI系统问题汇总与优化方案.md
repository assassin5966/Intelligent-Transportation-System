# 32 路 1080P 拉流与越线计数优化方案

> 适用环境：32 路 1080P、单卡 NVIDIA T4、32 核 CPU。工作区已实现部分修复；本方案和参数尚未完成现场部署与真值验收。

## 1. 结论

1. **先保证 32 路有画面、有处理、能落账，再提高有效处理帧率。** 推荐先验证单卡双引擎、960 检测尺寸、8 FPS 采样上限和 40 ms 组批窗口，并与单引擎、80 ms 窗口做对照。
2. 现场报告 GPU 利用率约 39%、CPU 约 35%、显存 2,412/15,380 MiB。资源读数支持开展双引擎试验，但不能证明处理能力或计数准确率。
3. 10 月 28 日日志中，54 次 FFmpeg 启动均回退 OpenCV；有统计的 26 个业务设备平均处理约 3.65 FPS，采样后加权丢帧约 43%。这是历史窗口数据，不代表当前 32 路的实测结果。
4. 日志没有人工真值，无法计算真实漏计或误计。必须用同一标注视频比较新旧方案，不能以 GPU 利用率、事件数增长或单项 FPS 宣布准确。

**容量参考：**若 32 路实际各采样 8 FPS，合计约 256 帧/秒；要满足采样后丢帧不超过 10%，总处理量约需 230.4 帧/秒，同时各路均需达标。8 FPS 是上限，不保证实际达到。

## 2. 问题与处理办法

| 问题 | 处理办法 |
|---|---|
| 视频缺失或拉流回退 | 核对 32 路与业务设备、GB 设备/通道的映射；检查实际 FFmpeg 后端、断流与 WVP 点播失败。同步查询失败按未知处理，不把它当作设备已删除。 |
| 处理帧率低、轨迹断裂 | 先对比单/双引擎，再分别对比 `interval/grid`、80/40 ms；按每路处理 FPS、最大间隔、采样后丢帧和真值选择。 |
| 线、方向或 ROI 错误 | 逐路校验计数线、锚点、方向和 ROI；非法配置不启用，凹形 ROI 的所有有效线段都参与判定。重点复核历史零事件、端点及点播失败设备。 |
| 重连、遮挡或空窗 | 按流会话隔离轨迹；长间隔或重连不能凭缺口两端位置虚构过线。记录缺口，有录像才按原配置复核或补算。 |
| 事件重复或对账不清 | 已确认事件与证据先落本地 SQLite，再以固定事件 ID 重试；逐 ID 核对后端账本和统计，差异隔离处理，不直接修改累计值。 |
| 跨摄像头统计 | 明确业务区域和镜头覆盖；同一目标经过多条线时，区分过线次数与区域去重人数，未经验证不做跨镜头自动去重。 |

## 3. 计数与数据规则

- **触发：**同一路、同一流会话中的有效轨迹，连续位置从线的一侧到另一侧，运动线段与 ROI 内有效计数线相交，且类别、方向、防抖条件均通过，才生成一次越线事件。
- **去重：**同轨迹同次越线只计一次；真实反向再次越线按方向和冷却规则处理。不同目标不能仅因位置或时间接近而合并。
- **异常：**无帧、低帧、存储失败或断流时标记不完整，不把未观察到的画面当作零流量。当前缺口时间来自本机 watchdog，非精确摄像头源时间。
- **落账：**事件保存 ID、设备、流会话、时间来源、类别、方向、轨迹和配置证据；同 ID 同内容幂等重试，不同内容冲突告警。默认是 `legacy` 协议，完整账本对账需另行验证并启用 `journal_v2`。

## 4. T4 试验参数及文件位置

### 4.1 部署机项目根目录 `.env.gpu`

更新或新增以下键，保留原文件中的其他配置。该文件由 [GPU 启动脚本](../scripts/start_all_gpu.sh)读取；本工作区没有现场 `.env.gpu`，以下是**试验目标，不是现场现值**。

```dotenv
INFER_MODE=gpu_batch
INFER_ENGINES_PER_GPU=2
INFER_SLOTS_PER_GPU=0
INFER_CAPACITY=32
INFER_SLOTS_MAX=32
INFER_HALF=true
INFER_BATCH_TIMEOUT_MS=40
INFER_QUEUE_MAX_BATCHES=2
INFER_MAX_QUEUE_AGE_S=2
DECODE_BACKEND=ffmpeg
DECODE_MAX_SHORT_SIDE=540
DECODE_FPS_SAMPLING=grid
# 下列值仅在 YAML 未设置对应项时作为回退
INFER_IMGSZ=960
DECODE_MAX_FPS=8
```

32 个槽位在双引擎下为每引擎 16 个；32 路接满后没有额外接入槽位。槽位表示接入上限，不代表已验证的推理吞吐。

### 4.2 [configs/business_rules.yaml](../configs/business_rules.yaml)

核对已有 `inference` 段；工作区当前为以下值，现场需另查：

```yaml
inference:
  imgsz: 960
  decode_max_fps: 8.0
```

- YAML 的 `imgsz`、`decode_max_fps` 分别覆盖环境变量 `INFER_IMGSZ`、`DECODE_MAX_FPS`。前者按批次热重载，后者对新建或重连的流生效；改动运行中挂载的 YAML 会影响现网。
- [GPU Compose](../docker-compose.gpu.yml)负责转发环境变量；`.env.gpu` 改动需重建 AI 容器，重建会中断计数并重置内存跟踪状态。`grid` 仅对 FFmpeg 生效，源 PTS 缺失时会保留输入帧。
- 现有 [1080P 试验文件](../configs/1080p-count-accuracy-trial.env.example)是**单引擎对照**；若作为后一个环境文件加载，会把双引擎值覆盖为 1。
- 计数防抖在 `business_rules.yaml` 的 `counting` 段，跟踪器参数在 [configs/bytetrack.yaml](../configs/bytetrack.yaml)；本组试验先保持现值。原方案的 `imgsz=640`、6 FPS 保留为单独对照；远景漏检时可另测 `.env.gpu` 短边 720 配合 YAML `imgsz=1280`。
- 如需启用 `journal_v2`，在 `.env.gpu` 先为后端设置 `MYSQL_ENABLED=true`、`EVENT_LEDGER_ENABLED=true` 并核验就绪，再为 AI 设置 `EVENT_DELIVERY_PROTOCOL=journal_v2`；具体切换和回退见[实施记录](./拉流计数实施记录与灰度操作.md)。当前自动补偿、权威账本重建和录像补算尚未完成。

## 5. 实施与验证

1. **建立基线：**核对 32 路身份、线和方向，保存当前代码、模型与参数；在 32 路同时在线时采集至少 30 分钟逐路 FPS、丢帧、最大间隔、批次、延迟、CPU 和 GPU 显存。
2. **单变量比较：**在两组总槽位均为 32 的前提下先对比单/双引擎，再分别测试 `interval/grid` 和 80/40 ms；其余条件保持一致。分 8、16、24、32 路逐级压测，最终以 32 路真实负载为准。
3. **核对实际生效：**查看 `/health` 的推理模式、两个引擎、槽位和组批窗口；查看 `/devices` 的 32 路实际解码器、源/输出尺寸、处理 FPS 和最大间隔。`next_connection` 仅代表下一连接配置。
4. **验证计数与容错：**用同一录像逐事件比较人/车、进/出、远景、夜间、遮挡、端点和相邻目标；测试断流重连、旧代帧、重复投递、ACK 丢失及持久化失败。影子试验使用隔离事件队列和统计库。
5. **分批上线与回退：**指标或真值下降、设备持续低帧、队列异常时停止扩批并恢复试验前配置；保留 outbox、账本、日志和缺口记录。`journal_v2` 必须先完成后端账本准备、协议兼容和对账验证。

## 6. 上线验收标准

| 项目 | 通过条件 |
|---|---|
| 设备覆盖 | 核对全部 32 路的身份、方向、ROI 和实际后端；连续 72 小时每路有效处理覆盖率 ≥99.9%，断流和故障时间计入分母。 |
| 处理能力 | 每路 ≥99% 的完整 30 秒窗口处理 FPS ≥5，且每路采样后加权丢帧率 ≤10%；同时记录最大处理间隔和延迟。不能通过降低采样或停路达标。 |
| 计数精度 | 对同设备、类别、方向的真值事件一对一匹配；人流、车流的精确率和召回率各 ≥95%，各自进/出及总数相对误差 ≤5%。每类至少 200 个真值事件、每方向至少 30 个；样本不足标为未验收。每设备/方向达到 30 个样本时，精确率和召回率各 ≥90%。 |
| 一致性 | 已持久事件在本地、后端事实账本和统计之间按同一水位及 ID/摘要核对；未关闭差异为 0，重试和故障恢复不重复应用、不丢失已提交事件。 |

验收还需覆盖相邻目标、端点、遮挡、掉头、重连和配置切换，每类至少 30 个标注事件；真值为 0 时报告误报数，不计算相对误差。无法取得真值或录像的场景标为未验收。现场 T4、32 路持续负载和人工真值尚未验证。

# 1080P 视频拉流与越线计数方案

日期：2026-10-28。本文按摄像头实际推送给 AI 的流均为 **1920×1080** 重新设计；延续项目目标：单台设备、单张 T4、32 路并发，每路有效处理帧率 ≥5 FPS，并以人工标注视频验证计数。32 路、25 FPS、T4 和目标帧率均是方案的压测前提，不代表已经现场确认或达标；编码格式、码率、实际帧率、CPU 核数和视频内容须逐路核实。

## 一、推荐链路

```text
摄像头 1080P → WVP/ZLM → FFmpeg 解码 → 选取原始帧、缩到 960×540
            → 每卡一个 YOLO11n 批量引擎 → 每路独立跟踪器
            → 坐标还原至 1920×1080 → ROI / 越线 / 去重
            → 事件持久化 → 后端幂等计数 → 实时统计与小时归档
```

采用已修复的批量链路，不以每路创建模型的 legacy 模式承担 32 路。`960×540` 是**待验证的推荐处理画布**，不是摄像头源流分辨率；计数线、ROI、轨迹和事件坐标仍使用流原始 `1920×1080` 坐标系。画面保留原比例、视场不变是自动按比例还原的前提；相机如果裁剪、变焦、镜像或改变宽高比，必须逐路重新核对标线和 ROI。

## 二、工作量与性能预算

以下均为理论算量或数据量，不是现场测试结果；未计解码器内部内存、额外拷贝、编码协议及视频内容差异。

| 项目 | 估算 | 含义 |
|---|---:|---|
| 32 路 1080P × 25 FPS 解码输入 | 约 1.66 G像素/秒 | 缩放和抽帧在解码后，不能视为只解码 8 FPS |
| 与 32 路 `4096×2336`、同帧率相比 | 像素量约 21.7%，降低约 78.3% | 仅像素量比例，不等于 CPU 耗时或设备容量比例 |
| 32 路 × 8 个 960×540 BGR 帧 | 约 398 MB/秒 | FFmpeg 向 Python 输出的理论原始帧数据量，实际还受帧率和拷贝次数影响 |
| 原配置 1706×960、同样每路 8 帧 | 约 1,258 MB/秒 | 改为 960×540 时理论管道数据量降约 68%；实际源帧率可能低于 8 |
| 32 路 × 5 有效 FPS | 至少 160 个完成处理的不同源帧/秒 | 不是源帧率、解码帧率，也不是批次吞吐 |

以 160 帧/秒为最低业务吞吐，若预留 20% 吞吐余量，需实测全链路可持续约 200 帧/秒。用平均每批有效帧数 B 估算，**完成一批的平均服务时间预算约为 B/200 秒**：B=8 时约 40ms，B=16 时约 80ms。这是容量核算条件，不是对 T4 性能的承诺；应计入预处理、预测、跟踪及调度的实际影响，不能直接拿单次 `predict` 耗时替代全链路吞吐。

当前 `select` 按输入帧时间戳挑帧，不复制帧，也不保证精确输出配置帧率。以**严格均匀 25 FPS** 为例，间隔阈值设 1/8 秒时可能每 4 帧取 1 帧，约为 6.25 FPS；实际结果受 PTS、起始相位及抖动影响。要达到每路 ≥5 FPS，应先测每路实际输出和最大帧间隔，不能把 `DECODE_MAX_FPS=8` 当作已经达到 8 FPS。

## 三、初始配置和生效条件

以下是**灰度起点，不是已验证的最优值**；现场使用 `docker-compose.gpu.yml` 时，以容器最终配置及规则文件为准：

```dotenv
INFER_MODE=gpu_batch
INFER_SLOTS_PER_GPU=0
INFER_CAPACITY=32
INFER_SLOTS_MAX=32
INFER_IMGSZ=960
INFER_HALF=true
INFER_BATCH_TIMEOUT_MS=80
INFER_QUEUE_MAX_BATCHES=2
INFER_MAX_QUEUE_AGE_S=2
DECODE_BACKEND=ffmpeg
DECODE_MAX_FPS=8
DECODE_MAX_SHORT_SIDE=540
STREAM_STALL_TIMEOUT_S=15
```

- 摄像头、WVP 和 ZLM 要确认 AI **实际接收**的流均为 1920×1080；不根据主码流/子码流名称推断分辨率。若 AI 拉到旧分辨率或发生裁剪，不纳入 1080P 验收。
- 当前 `configs/business_rules.yaml` 中明确配置了 `inference.imgsz: 960` 和 `inference.decode_max_fps: 8.0`，会覆盖环境变量。需要调整时，应同时核对规则文件的生效值，不能只改 `.env`。FFmpeg 的抽帧和输出尺寸在**建连时**确定，改帧率后要重建或重连流才会进入 FFmpeg 命令；不能仅凭规则热重载断言已生效。AI `/health` 的 `effective_config` 列出当前模型尺寸和下一次连接使用的参数；`/devices` 的 `processing_health` 显示该路建连时的采样上限、实际后端及帧尺寸。
- `INFER_BATCH_TIMEOUT_MS` 由模型池启动时读取；原先规则文件中未接入调度的 `inference.batch_timeout_ms` 已移除，不能通过规则文件热调调度窗口。调整该环境变量后需重建或重启 AI 服务，实际窗口可在 AI `/health` 的引擎快照中查看。
- 槽位 32 只是注册数量，不代表单卡实际吞吐或显存一定够。引擎无法初始化或容量满时应保持失败可见，不能自动回落多路 legacy。`INFER_MODE=auto` 可能转到 CPU 批量模式；上述起点显式使用 `gpu_batch`，避免把 CPU 批量误认为 GPU 已就绪。
- `960×540` 是按当前 `_ffmpeg_out_size` 和 `DECODE_MAX_SHORT_SIDE=540` 在标准 16:9 流下得到的输出。实际输出及回退情况以 `[ffmpeg] 解码就绪: 1920x1080 -> 960x540` 和 AI 的实际拉流日志为准；若 FFmpeg 打开失败自动退回 OpenCV，应告警并单列分析，不能算作 FFmpeg 方案达标。
- 当前代码将 `imgsz=960` 传给 Ultralytics；它不等同于“模型输入短边 960”。本机现有镜像 Ultralytics 8.4.131 的 `LetterBox(new_shape=960, auto=True, stride=32)` 对 960×540 和 1706×960 均生成 960×544 张量。这个结论只覆盖同形状、矩形填充及该实现条件，实际运行需要确认模型格式、rect 设置、批形状和版本。缩小 FFmpeg 输出可减少原始帧搬运，但两次缩放与一次缩放的图像质量可能不同，必须做计数对照。

## 四、计数与异常处理

1. **切换时逐路校准。** 检查 1080P 与原视频的视角、裁剪、镜像、标线方向和 ROI。原来基于 `4096×2336` 等分辨率的固定像素阈值在 1080P 下物理含义变化，不能直接认为已验证；先保持配置形成基线，再用标注视频评估 `min_motion`、ID 切换过滤和防抖参数。禁止无对照地统一放宽阈值。
2. **速度和连续性。** 按每个目标实际观察时间处理轨迹；连续失联超过当前 2.4 秒不推断跨间隔越线。`track_buffer` 仍以成功处理的帧数计量，不等同固定秒数。5 FPS 只是性能底线，不保证高速车、远处小目标或遮挡场景准确。
3. **流健康与恢复。** 区分设备在线、等待首帧、无新帧、推理停滞、低帧率和事件持久化受阻；重连后重置跟踪状态，旧代推理不能污染新流。单帧接收时间是本机解码接收时间，非摄像头采集 PTS；当前没有完整源到事件的真实延迟口径。
4. **事件与归档。** 越线事件先持久化再上报，后端使用事件 ID 幂等累计。持续监控 AI `/health` 的 `event_outbox` 积压及存储错误、后端 `/api/events/archive-status` 的待归档与隔离数量。迟到事件仅在小时数据完整、单归档调度器等条件下自动补偿；隔离事件须人工对账。Redis 账本、outbox 卷和存储容量须保留并监控。

## 五、实施与验收

### 1. 现场摸底

- 核实每路的实际流地址标识、分辨率、codec、源帧率、码率、GOP、视角及计数线；敏感地址和认证信息不得写入公开日志。选取白天、夜晚、快车、拥堵、遮挡、远景和人车混流素材。
- 在实际 AI 容器镜像内核对 FFmpeg、模型与 Ultralytics 版本、GPU 可见性、最终环境变量和规则文件；记录代码版本、配置快照、资源限制及硬件信息。此处不要求更换解码后端或启用 NVDEC；若 CPU 解码成为实测瓶颈，再单独核验 NVDEC 的支持、与推理共享资源后的容量及收益。

### 2. 画布与精度对照

固定同一段 1080P 标注视频、模型、规则、目标帧采样和输出口径，比较 FFmpeg `DECODE_MAX_SHORT_SIDE=540` 与原配置 `960`。逐点位、类别和方向统计人工真值、漏计、误计、重复、方向错误及事件时间偏差，并检查缩放/坐标与画线。优先选准确率达到业务门槛且资源占用更低的方案；业务门槛须由现场确认，不能仅用模拟车轨迹或“有事件”验收。夜间小目标若退化，保留对应点位所需画布，接受形状分组和容量重新评估。

### 3. 逐级负载与故障验证

按 1、8、16、24、32 路逐级压测，再以 32 路连续运行至少 1 小时；记录 30 秒窗口内每路有效 FPS、最大帧间隔、读帧/处理丢弃、各阶段等待、批量大小分布、CPU、GPU、显存、网络、事件积压与归档隔离。应覆盖断流、恢复、AI/后端重启、短时后端不可用和超容量注册。将 32 路同时达标视为验收条件，而非只看全局平均值。

当前实现提供处理 FPS、平均组批/执行器等待、平均预测/跟踪耗时、引擎批大小累计分布和排队/丢弃计数；另提供每路最近 30 秒的接收至计数及事件持久化完成耗时 P95/P99、样本数和已处理帧最大接收间隔。该时间从本机解码接收开始，不包含摄像头编码、源端缓存和网络拉流延迟，也不包含持久队列之后的后端应用时间；样本很少或完全无帧时不能将分位数当作稳定统计。`ffmpeg` 路径的 `grab帧` 与采样帧相同，无法据此计算源端主动抽掉的帧数；日志中内存快照队列的 `outbox丢弃` 不是持久越线事件丢失数。

### 4. 上线门槛与回退

- 必须同时满足：源流均为已核验的 1080P；32 路每路每个有效 30 秒窗口处理 FPS ≥5；真实标注视频按业务确认的精度门槛通过；无长期停流、旧代污染或无法解释的事件丢失；资源和持久化积压稳定。对断流窗口另行统计可用性，不能从分母排除后宣布全天达标。
- 先小流量灰度，记录并保留原始配置、版本和基线；验证正常后再逐步扩至 32 路。若 960×540 的小目标计数不合格，回退输出尺寸并重新测容量；若 GPU 或 CPU 负载不满足目标，减少接入路数或增加资源，不能以静默丢帧或 legacy 多实例代替验收。
- 保留原 Redis 与 outbox 持久卷，确认旧事件已处理并监控隔离数据；不要通过删除队列或关闭持久化来恢复性能。`appendfsync always` 对写入延迟的影响需在现场负载下实测。

## 六、本地实施与验证记录

- GPU Compose 默认使用 `gpu_batch` 和 `DECODE_MAX_SHORT_SIDE=540`；后端展示用的解码尺寸默认同步为 540。配置仍可由部署环境覆盖，摄像头流并不会因代码变更而自动变成 1080P。
- 为每路健康状态增加实际源/输出分辨率、是否 1080P、实际解码后端、建连采样上限和 30 秒本机处理延迟及最大帧间隔。非 1080P 流只告警并标记，不自动拒绝或改变坐标。
- 本地 1080P、25 FPS 合成 RTSP 流，使用项目镜像和 FFmpeg 实际拉流，日志显示 `1920x1080 -> 960x540`，约 3.02 秒收到 20 帧；该测试只验证单路链路，不是 GPU 推理吞吐或实际车辆识别准确率。FFmpeg 离线测试验证 25 FPS、上限 8 FPS 的选帧得到约 6.25 FPS，且不会补重复帧。
- 拉流 6 项、端到端模拟计数与质量指标 4 项、设备状态与有效配置 4 项、计数时间 8 项、批量调度与跟踪器 11 项回归通过；GPU Compose 格式检查通过。测试未覆盖现场摄像头、T4 32 路连续负载、真实标注视频或生产数据库。

# 拉流与越线计数逐问题解决方案

> 状态：本地代码和配置已按本方案分阶段修改；尚未部署或完成现场精度验收。具体已完成项、未完成项、协议切换及回退见 [实施记录与灰度操作](./拉流计数实施记录与灰度操作.md)。目标是在 1920×1080 源流下，提高人流和车流越线计数的准确性、连续性、一致性与可追溯性。
>
> 本文承接 [AI 系统问题汇总与优化方案](./AI系统问题汇总与优化方案.md)，保留其中原有的 FFmpeg 修复、960/640、80/30 ms 组批、8/6 FPS 采样、单/双引擎、端点和方向排查方案。原稿见 [审核前原稿](./AI系统问题汇总与优化方案_审核前原稿.md)。

## 1. 事实、目标与优先级

2026-10-28 日志覆盖 16:21:21–17:14:31，26 个设备有统计，54 次管道启动都发生了 FFmpeg 不支持 `-fps_mode` 后回退 OpenCV；2,221 个统计窗口平均处理 3.651 FPS，采样后加权丢帧约 43%。两个 WVP 通道各出现 89 次 480 点播失败；6 个有统计设备没有逐事件记录。用户确认现场 GPU 运行利用率不超过 40%。这些是已有观察，**不是已核实的实际漏计数量或各项改动的预期收益**。

以下为修改前工作区的隔离合成复现，保留作为问题基线；实现后的结果以实施记录和测试为准：

- **WVP 局部查询失败**：模拟 WVP 设备列表成功、单设备通道列表超时，`sync_once` 调用了一次停止管道并将该设备标为 offline。原因是查询失败后该设备通道没有进入 `wvp_channels`，后续被当作“通道已移除”。原日志没有记录该局部超时，故不能说当时发生了这个误停。
- **AI 运行列表未知被当成空列表**：日志第 72、14558 行记录了两次 AI 设备列表查询失败；当前 `_get_ai_running_devices` 出错后返回空集合，后续可能尝试停止并重新启动已有管道。本日志两次发生在 AI 服务启动前，**不能据此认定发生了误停**。
- **凹形 ROI 的有效线段被舍弃**：用 1000×1000 合成画面、水平线 `(0,500)→(1000,500)` 验证，U 形 ROI 的归一化顶点为 `[(.1,.1),(.9,.1),(.9,.9),(.65,.9),(.65,.3),(.25,.3),(.25,.9),(.1,.9)]`。线上的 `x=150` 和 `x=750` 均在 ROI 内，当前 `clip_line_to_roi` 只返回 `t=[0.65,0.90]`，把 `x=150` 所在的有效短段排除。日志不能证明现场点位实际采用了这种 ROI。
- **配置非法回退**：当前解析 `line_coords='invalid'` 得到默认竖线，非法 ROI 返回 `None`（随后视为未启用 ROI），可能造成在错误范围计数。合成复现说明代码路径存在，不代表日志中有该非法配置。

处理优先级按**影响计数的严重程度**和依赖关系排序：

| 优先级 | 事项 | 目的 |
|---|---|---|
| P0 | FFmpeg 兼容、WVP 误停、有效配置校验、ROI 有效线段、事件可靠提交 | 消除已确认的故障和可复现的错误路径 |
| P1 | 采样/组批/双引擎、目标识别与跟踪、方向与防抖、分类和设备拓扑 | 用同一真实视频降低漏计、误计和重复计数 |
| P1 | 事件时间、迟到补算、逐事件与小时汇总对账 | 保证已生成事件可追溯并正确归桶 |
| P2 | 细粒度 GPU 利用率、异常画质的扩展识别、长期容量优化 | 用实测持续改善吞吐和运行质量 |

P0 是工作排序，不表示日志已经证明所有场景造成了现场计数偏差。GPU 优化可与 P0 独立开展，不必等待全部账本改造完成。

修改前在隔离环境执行已有 `test_counting_time.py` 和 `test_device_health.py`，12 项测试及 6 个子测试通过；这些既有用例当时不覆盖上述全部发现。

## 2. 各问题的解决方案

### 2.1 FFmpeg 参数不兼容、拉流退回 OpenCV（P0）

**证据与原因**：日志中 54 次 FFmpeg 启动均报 `Unrecognized option 'fps_mode'`；当前 `app/ai/stream.py::_open_ffmpeg_reader` 固定传 `-fps_mode passthrough`。日志不能确定当前部署镜像的精确版本。

**实施方案**：

1. 启动 AI 服务时，对运行镜像中的 FFmpeg 进行一次无网络、短合成流能力检测。优先使用已验证可用的 `-fps_mode passthrough`，否则检测 `-vsync 0`；两个都不可用则回退 OpenCV，并记录明确原因。探测要有超时、缓存及失败日志，不能对每路反复启动探测。
2. 保持已有自动回退和重连，按实际设备记录请求后端、当前后端、失败原因、源/输出尺寸、采样配置和实际输出 FPS。不能以日志出现 54 次“就绪”作为 54 路在线证明。
3. 比较同一 1080P 视频在原输出尺寸和 960×540 输出尺寸下的识别精度、CPU/内存及每路 FPS；源尺寸始终作为坐标基准。解码后缩放会影响远处小目标，按第 5 节验收。

**验收与回退**：分别在支持、只支持另一参数、两个参数都不可用的环境验证首帧、持续帧、超时与重连；失效时安全回退，并在健康状态中标明。若真实视频精度下降，回退缩放尺寸或后端，保留设备与时间段的版本记录。

### 2.2 WVP 点播失败、同步误停和设备状态不准（P0）

**证据与原因**：两个通道长期返回 480；GAJK-4926 对应通道在两次 -10 后恢复连接。合成场景确认单设备的 `list_channels` 失败可能触发错误停流；AI 列表查询失败则被当成空列表。

**实施方案**（`app/backend/core/wvp_sync.py`、`wvp_client.py`、`api/devices.py`）：

1. 同步结果区分 `SUCCESS`、`EMPTY_CONFIRMED`、`UNKNOWN/FAILED`。每个 GB 设备单独标记通道列表是否查询完整。某设备列表查询失败时，只标记该设备数据过期并重试，**不把未返回的通道当成已删除或离线**；其他查询成功的设备继续同步。
2. `_get_ai_running_devices` 在超时、非 200 或解析失败时返回未知状态；该轮不按空集合发起删除或重启。只有成功返回的空列表才表示确实没有运行设备。
3. WVP 确认通道离线/移除、运维明确停用以及短暂查询失败采用不同状态。停止、删除和重新启动要求依据可信的完整快照或明确操作，保留原因与时间；设备身份以 GB 设备号/通道号绑定稳定业务 ID，名称变更不得自动删除原设备。
4. 对 480、-10、DNS 失败按设备/通道归并告警，分级重试并限制频率；保留最后成功时间。运维核对两个 480 通道的设备映射、网络/国标状态和是否需要参与业务计数。

**验收与回退**：构造“一个设备通道查询超时、另一个成功”“AI 列表超时/空列表/恢复”“真实离线”和“名称变化”用例；查询失败时运行中管道不被误停，真实下线仍按规则处理。保留旧状态机开关，切换前后对照设备清单和停止原因。

### 2.3 断流、重启和黑屏造成计数空窗（P0）

**证据与原因**：16:41:44 管道停止，26 台到各自下一次启动约 208.7–230.0 秒；首帧和恢复处理时间比启动更晚。当前状态只靠“设备在线/已注册”不能证明画面和处理有效。

**实施方案**：

1. 每设备区分 `WVP在线`、`管道已注册`、`已接收首帧`、`正常处理`、`断流/黑屏/冻结`、`持久化暂停`。记录 `stream_epoch`、最后有效帧、恢复首帧、首个处理成功及区间 `[缺口开始, 缺口结束)`。
2. 断流、长时间无新帧、黑屏/冻结或存储不可用时，相关统计显示“不完整”，不把无观察解释为零流量。重连后重置旧跟踪状态，隔离旧代结果，恢复正常需有新代真实帧。
3. 与现有 NVR 或分段录像对接，保留可按设备、时间检索的原始视频及配置版本。对有录像的缺口执行离线补算和差异审核；无录像时记录不可恢复时段，不能凭断流前后位置虚构过线。

**验收与回退**：断网、停服务、黑屏、重连和满盘测试中，缺口起止可查询、恢复可告警、旧代帧不计入新代；回放补算结果与原账先对账再入库。

### 2.4 非法计数线、锚点或 ROI 回退成默认配置（P0）

**证据与原因**：`app/backend/api/devices.py::_line_from_coords` 对非法字符串返回默认线；`_roi_from_coords` 对非法 ROI 返回 `None`；越界只告警。该路径经合成复现，可能计入错误区域。

**实施方案**：

1. 在设备配置接口统一校验：数字有限且归一化坐标在 [0,1]；线两端不重合；锚点不落在线上；ROI 顶点数不少于 3、有效面积非零、没有自交。线与 ROI 无有效交集时禁止启用计数。
2. 区分“用户明确关闭 ROI”与“ROI 解析失败”；非法配置返回明确错误，不替换为默认线或全画面 ROI。对于已有历史配置先只读扫描并出清单，错误设备显示 `CONFIG_INVALID`、暂停该路计数和告警，保留原配置供修复，不改写其他设备。
3. 保存 `config_version`、生效时间、线/锚点/ROI、类别与方向规则；新配置保存失败不能覆盖上一份有效配置。灰度时先做现场画面预览和方向确认。

**验收与回退**：空值、非法字符串、NaN/Inf、越界、退化线、锚点在线上、ROI 自交和无交集均返回可定位错误；合法的“明确关闭 ROI”仍能使用。回退到上一有效版本后，每个事件能追溯到该版本。

### 2.5 ROI 外拒绝和凹形 ROI 的多段计数线（P0）

**证据与原因**：窗口累计 `ROI外=52480`，但它是轨迹帧次数，不能解释为漏计量。当前 `ROIDetector.clip_line_to_roi` 只保留最长有效子段；`LineCrossingCounter.process_tracks` 又在判线前以当前点是否在 ROI 内作为准入，因此薄 ROI 或快速目标可能在一次跨越后当前点已离开 ROI 而被拦截。

**实施方案**：

1. 将线和多边形求交改为返回**所有**在 ROI 内的有效参数区间；排序、合并重叠/相邻区间，按明确的边界容差判断交点属于任一区间。线段与 ROI 完全不交时禁用该线并告警。
2. 越线候选检查运动线段与计数线的真实交点及该交点是否位于有效 ROI 线段。对跨线确认中的轨迹保持状态连续；同时保留连续观测与方向/防抖约束，防止把延长线或单纯穿过 ROI 边界当成过线。
3. 更新配置预览和可视化，显示每一有效线段。新旧接口兼容期间，不能让旧界面只显示一段却仍使用多段计数；未升级客户端必须提示或暂不允许保存多段 ROI。

**验收与回退**：U 形 ROI 横线的 `x=150`、`x=750` 两个交点都可触发；两段之间、ROI 外、线段延长线、共线边界和仅触碰端点不误计。薄 ROI 快速进出和跨线后移出 ROI 的轨迹各有回归；支持按设备回退旧规则。

### 2.6 采样后丢帧、低有效 FPS 和时间口径（P1）

**证据与原因**：日志设备窗口平均处理 3.651 FPS、采样约 6.435 FPS，采样后加权丢帧约 43%。当前取最新帧，过载时中间帧被覆盖；FFmpeg `select` 的输出 FPS 未必等于配置值。本机 25 FPS 合成流设置上限 6 FPS 时约输出 5 FPS。

**实施方案**：

1. 保留原方案的 8/6 FPS 对照，不直接把配置值当实际帧率。统计每路源/采样/处理 FPS、连续处理间隔分布、最大间隔、覆盖丢弃和推理饱和丢弃；记录源 PTS 可用性、连接代次和实际后端。
2. 根据相同视频测 8、6，以及确有需要时的其他采样上限；选择能满足第 5 节精度和 FPS 的组合。对 25 FPS 源，当前时间间隔选帧会量化；若要实现更均匀的目标采样，需以可靠源 PTS 或接收单调时间维护明确的下一采样时点，**不复制帧、不伪造中间帧**。现有 FFmpeg rawvideo 管道没有携带源 PTS，必须先解决时间戳伴随传递或标明只能按本地接收时间采样。
3. 保留实时路径最新帧与有界背压，但每路须有公平服务和最长帧龄限制。无法满足容量时显式降级、记录缺口或增加算力，不能靠无限排队、停设备或只降低采样分母让丢帧率看起来达标。
4. 速度和防抖间隔采用该目标相邻两次有效观测的单调时间。墙钟回跳、时间乱序、重复帧与超长间隔均不推进正常计数；缺失源时间的事件标记 `local_decode_receive`。

**验收与回退**：25/15/8/低于目标的源 FPS、抖动/重复/乱序/PTS 回跳和断流恢复下，不产生复制帧；每路统计与实际输出一致，按相同视频同时比较 FPS、帧间隔与真值。新采样算法保留后端开关与旧实现作为回退。

### 2.7 GPU 利用率 ≤40%、组批与单卡双引擎（P1）

**证据与原因**：用户确认现场 GPU 利用率 ≤40%。当前 `gpu_engine.py` 每引擎一个执行线程，`predict` 后逐路转回结果并调用 tracker；原日志的 182 ms/批是设备窗口指标，不能简单视为纯 GPU 时间。调整 `INFER_QUEUE_MAX_BATCHES` 不会把单个执行线程变成多个推理线程。

**实施方案**：

1. 在现场同期记录 GPU、CPU、输出形状、每个引擎队列及唯一批次的预处理/推理/数据回传/逐路跟踪/批完成时间，先区分缺帧、形状碎片和串行处理。检测结果 `xyxy/conf/cls` 目前分别执行 `.cpu()`；试验合并取回并验证顺序、坐标、类别及空检测等价。
2. 保留原方案双引擎：在 `model_pool.py` 增加明确开关，候选为同一 GPU 上两个独立引擎，设备按可用容量分配；每引擎独立模型和 tracker，不能跨设备共享可变跟踪状态。单引擎仍是回退。比较同一视频的四组：**960/单、640/单、960/双、640/双**；额外单变量比较 80/30 ms 组批窗口和采样上限。
3. 若跟踪/回传确实阻挡后续推理，试验单模型推理线程 + 按设备串行的有界跟踪工作队列，保证每设备帧序、流代次、超时和取消语义；不要取消每路在途限制，也不要通过无界队列换 GPU 利用率。
4. 如采用更小输入或其他推理引擎，记录模型、输入张量实际尺寸、精度、NMS 和转换版本；按远景小人、小车、夜间及遮挡真值分别验证。

**验收与回退**：四组在同一视频及标注上比较每路 FPS、采样后丢帧、处理间隔、事件 Precision/Recall、GPU/CPU/显存；并发超载、请求取消、设备重连均不能错路、乱序或遗留请求。实测综合表现不达标时回退单引擎或原模型尺寸。GPU 利用率是诊断指标，不作为精度通过条件。

### 2.8 跟踪 ID 切换、遮挡和观察间隔（P1）

**证据与原因**：日志有 1,055 条轨迹缝合信息，`ID切换=0` 仅表示现有检测器未报。当前 `configs/bytetrack.yaml` 的 `track_buffer=60` 以跟踪更新帧为单位；`traj_state.py` 的缺失宽限为 2.4 秒、缝合窗口 0.48 秒，两套时间尺度可能随有效帧率变化而不一致。

**实施方案**：

1. 按设备记录 tracker 输入 FPS、轨迹最后观测时间、ID 切换/缝合候选及是否成功、类别和运动一致性；通过真实回放标注断 ID 与错误合并，先确定需要调哪一项。
2. 以真实观测时间管理缺失与缝合，合理映射第三方 tracker 的帧量纲；不同 FPS、短时遮挡、密集并行目标分别调参。不能简单把 2.4 秒延长为 tracker 保留时间，否则可能把不同人/车拼成同一目标。
3. 高可信缝合须转移越线状态和已计数记录；关联不明确时不自动合并、不自动生成补计，记录待复核事件。间隔无效或大于配置上限时重置并记录缺口，不从两端点推断不可观察的整段动作。

**验收与回退**：同车遮挡后复现、两车并行、不同类别相邻、快速换 ID、慢车停留、2/3/5/8/25 FPS 和 2.4 秒边界均测试；对照人工轨迹的漏计、重复和 ID 误合并。旧参数按设备可回退。

### 2.9 越线触发、方向和六个零事件设备（P1）

**证据与原因**：6 台设备的逐事件日志为 0；原方案已指出并非都能认定为方向配反。现有 `count_only`、锚点、ROI 和摄像头类别共同决定事件是否输出，`单向模式` 统计还可能混入更早的去重/冷却拒绝。

**实施方案**：

1. 对每条线明确“锚点所在侧为内侧”，外→内为 Enter，内→外为 Exit；先确认该设备实际业务方向、摄像头类别、ROI 与单/双向模式。
2. 对已确认有效轨迹，保存上一个明确侧别。轨迹进入线上容差带时保持等待；离开到另一侧且轨迹线段与有效计数线有交点、时间间隔有效时产生**候选**。随后按防抖、方向、类别和去重决定是否生成事件；恰好落在线上、沿线移动、线段延长线和原侧返回不能重复计数。
3. 逐台核查 221014、193011、193012、193013、193014、223016 的真实片段、有效连接时间和配置；仅在确有物理方向/配置错误时变更锚点或 `count_only`，记录版本和操作人。
4. 将拒绝原因拆分为 `方向禁用`、`同轨迹重复`、`反向冷却`、`ROI外`、`交点在线段外`、`速度不足` 等互斥结果。原方案的 80%、≥10 次、连续 3 窗口可以作为**人工排查告警候选**，需在原因拆分后以流量验证，不自动翻转方向。

**验收与回退**：逐台提供有真实目标通过的片段或明确记录无样本；正反向、线上停留、反向返回、越线后出画、异常方向配置均有预期事件结果。切回设备上一配置版本可恢复原方向。

### 2.10 端点、夹角与防抖可能误杀或误计（P1）

**证据与原因**：日志有端点过滤 286 次、所谓夹角过滤 282 次；当前后者还混合了交点在线段外的情况，拒绝次数不等于漏计数。

**实施方案**：

1. 保留原方案“端点敏感半径按线长比例”作为候选；按原画面比例设置上下限，与原按画面长边策略对照，重点验证 GAKK-0017/216012 的端点场景，避免短线半径过小引入误计。
2. 在 `crossing_detector.py` 和 `counter.py` 拆分速度不达标、交点超出有效段、触线未确认等原因；以法向速度和真实目标观测间隔判断，阈值以 px/s 和配置版本记录。
3. 防抖以明确侧别、保持时长与实际观察为依据；同一轨迹反向真实掉头可产生新事件，沿线抖动或起止同侧不产生新事件。原阈值与新阈值通过标注片段比较，不能以拒绝数下降替代准确率。

**验收与回退**：端点通过、端点旁绕行、延长线穿越、贴线运动、慢速穿线、噪声抖动与快速掉头分别核对 FP/FN；新旧阈值可按设备切换。

### 2.11 目标分类和多摄像头重复统计（P1）

**现状**：当前 `app/ai/__init__.py` 将 person/bicycle/motorcycle 归人流，car/truck/bus 归车流；同一物理目标可能经过多个摄像头。计数的业务口径尚需现场确认。

**实施方案**：

1. 将检测类别→业务类别、行人与骑行目标的关系配置化并版本化；未知类别不默认当成车辆，进入待审核。每台设备明确允许人、车或混合。保留现有类别映射作为兼容模式；若业务确认“骑行人及其自行车算一人”，再启用按轨迹、位置和时间的一对一关联，关联不确定时标记复核，不能同时自动当作两个独立人。无人骑乘自行车如何计数需由业务明确，不在本方案中擅自改变。
2. 建立“摄像头→物理线→入口/出口→区域”的归属清单；先明确指标是“每条线越线次数”还是“区域去重人/车辆”。如同一入口有重叠镜头，优先指定唯一主计数线；备用切换使用明确的生效时段和版本。
3. 只在有可靠跨镜头身份/录像证据时做跨摄像头关联。无法证明同一物体时保留可追溯事件并标记待核，不能仅因时间地点相近自动去重，也不能盲目把重叠镜头相加当独立人数。

**验收与回退**：行人+自行车、摩托/机动车、两个相邻目标、同一目标跨重叠摄像头、主备切换和多次真实往返逐条核对；配置切换可回溯。

### 2.12 视觉去重、事件落盘和重复投递（P0）

**证据与原因**：当前已具备 SQLite outbox、稳定 `event_id` 重试和 Redis Lua 幂等；但 `counter.process_tracks` 先在内存标记已计数，随后 `pipeline.py` 才入队，进程在二者之间退出可能遗漏尚未落盘的候选。当前传输只发送事件 ID、设备、类型和时间，后端缺少完整轨迹证据。

**实施方案**：

1. **视觉去重**按 `device_id + stream_epoch + line_version + track_lineage + crossing_sequence` 组织候选状态。同一轨迹同一跨线确认只产出一次；明确完成后又真实折返/再次通过可生成新序号。高可信轨迹缝合须转移候选及已计数状态；不同目标不能仅因同点、同秒而合并。
2. 将计数器改为先产生候选和待提交的状态变更；本地 SQLite 在同一事务写入候选/事件、状态变更和待发送任务，提交后才推进内存的已确认状态。重启从已提交状态恢复；每个事件生成一次 `event_id`，所有网络重试复用同一 ID 和规范化 payload。
3. 扩充事件契约：设备、流代次、线/配置版本、目标类别、方向、轨迹及缝合来源、交点、事件时间来源、模型版本和视频证据引用。对同 ID 同 payload 返回幂等确认；同 ID 不同 payload 返回冲突并隔离报警。
4. 存储不可用时暂停该路事件确认，保留失败候选、报警并标记缺口；恢复后继续提交。进程在本地事务**提交前**崩溃造成的未观察事件，只能用原始录像重放；不能声称事务能恢复未被视觉系统看到的目标。
5. 后端建立权威事件明细与物化任务：建议在 MySQL **同一事务**写事件明细及待物化记录，成功后返回“已持久接收”；Redis 实时/小时统计由任务按 `event_id` 幂等更新。不能把 MySQL 与 Redis 的两个独立操作视为一个事务。Redis 故障期间报告物化滞后，恢复后按明细重建或补投。
6. 与旧协议兼容：新旧 API/能力声明分阶段并行，旧客户端不带 ID 的事件必须显式标记为弱幂等；设备切换前先排空本地队列、确定切换水位并确保同一设备只有一个正式生产者。影子试运行使用隔离存储。避免把“已持久接收”误称为“已应用到 Redis”。

**验收与回退**：提交前后杀进程、ACK 丢失、重发、并发相同 ID、相同 ID 不同内容、SQLite 满盘、Redis/MySQL 不可用及重启均注入；**已提交事件**不丢失且只应用一次，未提交时段有缺口/录像依据。回退前排空队列并按事件 ID 对账，不删除未交付事件。

### 2.13 事件时间、迟到归档和当前数量（P1）

**证据与原因**：当前事件时间使用本地接收时间插值，无法证明是摄像头采集 PTS；Redis 当前总数有非负钳位，设备值直接增减，乱序或迟到可能造成当前值不同。

**实施方案**：

1. 保存事件发生时间、确认时间、后端接收时间、时间来源和时区；可用可信源 PTS 时关联源时钟，否则标记本地接收时间。小时/日桶统一按业务时区的事件时间、左闭右开区间归属。
2. 给已归档小时增加版本/水位，迟到事件在完整明细可用时重算并重归档；小时信息缺失、超保留期或版本竞争时隔离，不用局部数据覆盖完整 MySQL 记录。
3. 以经确认的区域初始值、进入、离开及经审核补偿重算当前值；无完整边界、初始值或有未恢复缺口时显示“不完整/未知”。如展示层需要非负值，仍保留原始差额和异常，不直接覆盖事实。

**验收与回退**：跨小时/跨日、夏令/时区配置、乱序、重复、迟到、桶过期、Redis 失效、并发归档和缺初始值均有测试；旧报表与新账本按水位对照后切换。

### 2.14 统计对账、健康与原因定位不足（P0/P1）

**实施方案**：

1. 统计至少分为：源有帧、采样、处理、候选、已确认、已落盘、后端已接收、已物化、已归档，以及拒绝/缺口/隔离。所有计数标明设备、时间窗口、流代次和配置版本；每个候选记录一个主要决策原因。
2. 按同一生产者、设备/线/类别/方向和水位做逐层对账。设本地已提交事件为集合 `C`、后端已持久接收事件为 `B`、本地待投递/隔离事件为 `P`：`C - B` 中的每个事件必须能在 `P` 中找到；`B ∩ P` 表示后端已接收但本地仍待确认，例如 ACK 丢失，不能重复相加。分别核查 ID 和 payload hash，补偿事件单独归类；权威事件按同一水位聚合后，再与 Redis 和已完成 MySQL 小时桶比较。保留已确认事件的本地审计记录，不能只用成功后会删除的待发送队列当历史账。
3. `/health` 聚合实际后端、FFmpeg 失败、事件队列积压和最老年龄；`/devices` 展示逐路 FPS、最大间隔、缺口、配置及处理状态。设备在线但无有效帧、无有效配置或事件存储暂停，均不可显示计数健康。
4. 生成每日对账与现场真值复核报告；发现异常时冻结受影响桶版本、人工核因，用原 ID 补投或可追溯冲正/补偿事件修正，再重算。无原始视频时标记不可验证。

**验收与回退**：注入不同阶段丢失、重复、迟到、隔离和积压；每个差异能被定位，异常不标记为正常。统计窗口未满和服务重启时要输出完整性状态，不把部分窗口作为完整对账依据。

## 3. 统一事件触发、去重和数据流

```text
WVP/设备校验
  → 首帧/时间/分辨率/有效状态校验
  → 有界采样与按形状组批
  → 检测类别、逐路有序跟踪
  → 多段 ROI 内的真实线段交点 + 锚点方向
  → 防抖/单向规则 → 候选 ID
  → 同轨迹去重 / 真实反向或再次通过
  → SQLite 候选+状态+待发送任务同事务
  → 后端事件明细+物化任务同事务
  → Redis 幂等物化 → MySQL 小时版本化归档 → 对账
```

任一阶段信息不足时进入对应 `PENDING/INVALID/GAP/QUARANTINED`，记录原因和时间，不将状态冒充成功计数。已持久事件的交付幂等与现实目标的视觉去重是两件事：前者可按 event_id 严格验证；后者仍需视频和轨迹证据确认。

最低自动化和故障注入用例：

- **并发性能**：1/8/16/26 路及实际目标路数、不同 shape 和密度、1/2 引擎、慢 tracker、队列饱和、请求取消；检查每路公平、事件顺序及资源。

## 5. 准确率和上线验收

以下为建议验收门槛；业务要求更高时按业务要求。**模型输出事件数增加、GPU 利用率提高或拒绝数下降都不能单独证明准确率改善。**

1. **真值数据**：覆盖 26 台线/方向/ROI 配置；针对 6 台零事件设备逐台拿到有目标通过的片段或标明未验收。包含白天/夜间、远/近、小目标、遮挡、拥挤、端点、掉头、两相邻目标、断流重连和不同方向。标注设备、线、类别、方向、真实越线时刻和交点，由第二人复核；保存视频哈希和配置版本。
2. **逐事件匹配**：在已校准的视频时间轴上，按设备、线、类别和方向进行一对一匹配；建议初始匹配容差为越线时间 ±1 秒、交点沿线位置偏差不超过线长的 10%，容差须在试验前固定并由标注人员确认。相近的多个目标出现匹配歧义时人工复核，不能让一条预测匹配多个真值。
3. **精度指标**：分人/车及 Enter/Exit 计算 `Precision=TP/(TP+FP)`、`Recall=TP/(TP+FN)`、方向错误、重复数及 `|预测-真值|/真值`。建议每类整体 Precision、Recall ≥95%，各方向及总数相对误差 ≤5%；每类至少 200 个真值、各方向至少 30 个。单设备/方向样本 ≥30 时分别要求 Precision、Recall ≥90%；样本不足标为未验收。真值为 0 时列误报数，不能计算相对误差或把零事件当通过。
4. **覆盖和吞吐**：按应在线时间计，连续 72 小时每台有效处理覆盖 ≥99.9%；每台应在线的完整 30 秒窗口中 ≥99% 的窗口处理 FPS ≥5，采样后加权丢帧 ≤10%。无帧/故障窗口纳入分母；实际场景需要更高 FPS 时以真值实验结果为准。
5. **一致性**：已持久提交事件在本地、权威明细、Redis 物化和 MySQL 已完成小时之间按 ID/水位对账；未解决差异、丢失和重复应用为 0。缺口无法获取录像时标记不可恢复，不能声明该时段计数完整。
6. **运行稳定与回退**：记录每设备在线/有效帧、队列、异常和版本；若精度、覆盖、投递或对账失败，停止扩批、保留证据并回退。最终验收报告包含每台设备、每方向样本数、FP/FN、缺口和未通过项。

现场录像、带标注的真值、通道映射及目标部署环境是准确率验收的必要输入。本方案能明确修复路径和验证方法；在这些输入及现场测试完成前，不能承诺彻底消除所有计数误差。

## 1. 结论和适用边界

1. 已证实的链路问题是：FFmpeg 启动命令含当前运行环境不支持的 `-fps_mode`，54 次启动均回退到 OpenCV；26 个有统计的设备处理帧率偏低，采样后覆盖丢帧较多；两个 WVP 通道长期点播失败；一次服务停止与重启造成确定的处理空窗。这些会降低覆盖能力和轨迹连续性，是计数风险，但**日志不能量化实际漏计或误计数量**。
2. 在本日志中，AI 越线事件日志与后端事件日志各 268 条，按设备和事件类型汇总一致；日志没有逐事件 ID，无法证明逐条交付、去重、Redis/MySQL 持久性或真实世界计数准确。运行统计窗口里的事件之和为 266；与 268 条逐事件日志的差值可由一条停止前未满窗口、一条文件截断前未满窗口解释，见第 2.4 节，不能据此证明逐事件交付成功。
3. 用户已确认现场 GPU 利用率不超过 40%，原方案中的 39% 是原作者记录的现场观测；因缺少与 10 月 28 日各路窗口对齐的采样序列，目前不能复算该时段的 GPU 均值或单凭它确认瓶颈。改 640、双引擎的具体收益以及由过滤次数推导的漏计数仍需实测；小目标召回、重叠摄像头、重启空窗、事件持久化故障及时间/配置版本需要补充闭环。
4. 本次日志缺少原始视频、逐对象人工标注、完整配置历史、WVP 通道与业务设备的权威映射、GPU 原始采样和事件账本。因此本方案为可实施规范；**准确率必须经带真值的视频回放与现场验收才能判断，不能从一份日志保证绝对准确**。

### 2.3 流处理与推理现状

当前代码链路为：

`WVP 设备同步/点播 → ZLM 流地址 → FFmpeg 或 OpenCV 拉流/解码 → 采样与预处理 → GPU 同尺寸组批 → 每路跟踪 → ROI/计数线及规则 → 事件落本机 SQLite outbox → 后端事件 API → Redis 实时/小时桶 → MySQL 小时归档`。

推理回传后该路才提交下一帧；读取线程与其他设备并行，最新帧可覆盖未处理帧。相同尺寸分组是为了使同批模型输入形状一致，避免不同尺寸导致额外 padding 或推理形状问题；此机制本身不是已证实的漏计根因。按日志可复现：

| 指标 | 全部窗口结果 | 解释 |
|---|---|---|
| 单路处理 FPS | 均值 3.651，P50 3.60，P95 3.83，最大 6.83 | 窗口值的分布；2,174/2,221 个窗口低于现有 5 FPS 告警线 |
| grab／采样 | 总 grab / 总窗口秒数 ≈24.845 FPS；采样 ≈6.435 FPS | 连接采样配置在看门狗中可见为 8.0，不等于实际输出 8 FPS |
| 采样后丢帧 | 窗口平均 42.543%；184,379 / 428,793 ≈43.000% | 不包括主动采样节流；窗口内采样、处理对齐和重连口径有近似误差 |
| 推理批次／等待 | 均批 24.683，推理 182.347 ms/批，组批等待 31.082 ms，执行器等待 2.792 ms | 按设备已处理帧归属的批次结果汇总；不是引擎去重批次均值 |
| 接收至完成／预处理 | 386.316 ms、33.277 ms/帧 | 为本机解码接收后到该帧处理完成；不含摄像头采集到本机的全部延迟 |

稳定子窗口 16:30–16:41 与 16:50–17:14 的每窗口平均处理 FPS 分别为 3.610 和 3.568，采样约 6.361 和 6.495 FPS。两段均覆盖 26 个不同设备，但窗口仍未严格对齐。不能由 `26 × 单批大小 / 单批耗时` 得出全系统实测吞吐，也不能仅凭平均等待或未提供的 GPU 利用率确定唯一瓶颈。应补充端到端打点和按引擎唯一批次统计。

### 2.4 越线事件和疑点

- AI 与后端日志各记：PersonEnter 147、PersonExit 73、VehicleEnter 44、VehicleExit 4；26 台的事件类型分组也一致。日志未带 `event_id`，同一类型的多条事件可能互相抵消，不能逐条核销。统计窗口事件数为 266：GAJK-4925 在 16:52:43.385 汇总后、16:52:46.143 停止前的 16:52:45.421 有 1 条 PersonEnter（21249、21282、21292 行），未满窗口未汇总；GAJK-3518 在最后一次 17:14:10.430 汇总后的 17:14:11.005 有 1 条 PersonExit（41121、41125 行），日志结束前窗口未满。两条附近均有同设备/类型后端日志。由此可解释统计口径差 2，但由于日志缺事件 ID，仍不能证明逐条严格对账。
- 窗口拒绝累计：历史不足 69,022、ROI 外 52,480、未远离线 603、端点过滤 286、夹角过滤 282、单向模式 76、滞留未满 1。它们是轨迹在帧/步骤上的拒绝次数，同一对象可重复出现；不能直接当成漏计物理对象数或计算准确率。
- 当前 `counter.py` 对 offset 异号但未检测到越线的情况统一记为“夹角过滤”；而 `crossing_detector.py` 还会因交点落在有效线段之外等原因返回空，因此 282 并非全是角度或速度问题。当前 `can_count` 合并了同轨迹去重、反向冷却和单向过滤，调用方在拒绝后按方向标注“单向模式”，原因可能混淆；不能直接用该数字构造精确反向比例。

### 2.5 当前配置和日志版本的区别

当前工作区 `configs/business_rules.yaml` 是 YAML 优先、缺省才回退环境变量：`imgsz=960`、`decode_max_fps=8.0`；当前文件中的 `min_distance_ratio=0.005`、`hysteresis_ratio=0.01`、`endpoint_sensitivity=0.02`、`min_motion=0.5`、`hold_frames=1`。按当前代码及 1080P，前两者受 20 px 下限约束均为 20 px，端点半径 38.4 px，速度阈值为 12.5 px/s（按 25 FPS 基准），保持时长 0.04 s。端点过滤还要求连续两次位置都靠近同一端点，并非“距离端点小于半径即拒绝”。

## 4. 完善后的实现规范

### 4.1 设备、拓扑和配置：先确定“应该计什么”

1. 建立稳定业务设备 ID 与 WVP 国标设备/通道/ZLM 地址的映射，配置当前是否应在线、摄像头功能、人/车口径、物理入口/出口、归属区域及计数线。日志中的设备名称可变，不能作跨系统唯一键。
2. 每条线保存归一化端点、ROI、多边形、代表业务内侧的锚点、允许类别、允许方向、坐标参考尺寸、阈值和配置版本；保存人、审批人、时间、启用时间和变更前后内容。生效版本应能关联每个事件及流会话。
3. 保存时校验坐标有限且在 [0,1]、两端点不重合、ROI 至少三个不共线顶点且不自交、线与有效 ROI 相交、锚点不在线上或边界容差内；对场景遮挡、线与实际运动方向、锚点物理含义由现场人员确认，几何合法不等于业务正确。
4. 保留 `person/bicycle/motorcycle → 人流，car/truck/bus → 车流` 的当前默认映射作为待业务确认项；明确骑行人和车同时检出的去重口径、未知类别和新车型处理。未经授权，不按“未识别即车辆”兜底入账。
5. 画出每个区域完整边界及设备覆盖。多摄像头重叠、双向卡口和同一目标先后经过多条线时，区分“过线次数”与“去重后的区域人数/车辆数”；没有经过校验的拓扑或跨摄像头关联能力，不把多机事件直接相加当独立人数，不做基于时间接近的自动跨机去重。
6. 配置变更采用先验证、预览、灰度、切换的单一事务版本；连接时固定的采样参数需重连后报告生效，热更新参数要报告切换帧/时间。老的 CROSSING 状态继续按原配置完成或标记为未确定后重置，禁止前后配置混用产出事件。系统记录生效配置哈希和来源，以便复放。

### 4.2 拉流、时间和覆盖

- 每路维护 `stream_epoch`，连接、首帧、最后帧、首个处理成功、异常、重连及恢复均写时间和原因。WVP 失败按设备/通道/状态码归并、指数退避和抖动，持续监测并告警；设备状态为“在线”不能替代“正常有帧、有处理、可落账”。DELETE 404 按 API 语义确认是否幂等，不隐藏其他错误。
- 记录预期在线时间、有效有帧时间、有效处理时间、精确缺口 `[start,end)`、源/输出分辨率、解码器及实际采样、帧到达与处理间隔。网络断流、长间隔、黑屏/冻结、错误尺寸、排队过载、存储不可用均形成可查询的无效或降级时段；数据展示为不完整，禁止把无观察当作零流量。
- FFmpeg 启动前在**部署镜像内**查询版本并用短合成流探测参数和输出帧；优先使用该镜像实际支持的选项，失败按原因回退 OpenCV，暴露当前后端和连续失败次数。测试解码器首帧、持续输出、异常退出、颜色/尺寸/坐标、抽帧和重连；不要让回退无限掩盖故障。
- 以单调时钟计算帧间隔和超时；保留本地接收墙钟、处理完成时间以及可用的源 PTS/采集时间、时区、时间可信状态。源时间不可用或回跳时显式降级，不能把解码接收时间称为摄像头采集时间；主机时钟突变时不可产生负间隔或跨日错桶。发生分辨率变化须重算比例并保留同一规范化线坐标，不合法时暂停该路计数。
- 对可靠的视频来源，保留可索引的原始片段或对接 NVR，至少覆盖故障发现与人工复核/补算约定期限；落地前由运维确认容量、权限、保留天数与查取能力。录像不可用的缺口只能标记不可恢复，不能宣称事件零丢失；回放必须使用原始配置版本和去重/补偿规则。

### 4.3 检测、轨迹、越线和拒绝规则

1. 原始帧坐标为几何基准，按每轴比例把检测框和中心从输出帧映射回原始分辨率；记录原始、输出、模型实际输入尺寸及版本。验证横纵缩放、letterbox 还原、裁剪边界、非 1080P 和重连切尺寸。
2. 轨迹在同一 `device_id + stream_epoch` 内顺序更新，使用有效且递增的单调时间；采样抖动、低帧率、帧重复、乱序或时间无效分别记录。无法确认连续观测、超过失联上限、ID 切换/重连时，不凭两帧跨越一个大缺口直接创造事件；产生“待复核缺口”并允许视频补算。轨迹缝合只在时间、空间、类别和运动一致时尝试，并保留前后 ID 与证据；不确定时不静默合并。
3. 触发候选须满足：目标属于允许类别；有效轨迹至少有先后两个可用位置；确认前满足 ROI 准入；轨迹从线一侧到另一侧，运动线段与**ROI 裁剪后的有效计数线段**有交点；方向根据锚点定义的内外侧确定。恰好落线、浮点容差、沿线移动、越过延长线、端点及 ROI 边界均应有明确状态和测试，不能两次触线重复计数。
4. 对候选执行速度/角度、远离线距离、端点、保持时长、滞回、ID 切换、反向冷却、单向业务规则；阈值单位固定为像素/秒或归一化尺寸/秒，并随分辨率和配置版本明确换算。防抖基于有效观测时间，低帧率不能无限放大容忍时间；掉头或走回真实反向穿线在规则允许时应产生新事件。
5. 现有拒绝码拆成互斥、可枚举的首要原因（如 `INSUFFICIENT_HISTORY`、`ROI_OUT`、`CROSS_OUTSIDE_SEGMENT`、`LOW_NORMAL_SPEED`、`ENDPOINT`、`HOLD_PENDING`、`SAME_TRACK_DUPLICATE`、`REVERSE_COOLDOWN`、`DIRECTION_DISABLED`、`OBSERVATION_GAP`）。每条候选生成稳定 `candidate_id`，保存必要位置、时间、线/配置版本和决策；仅对候选分类计数，轨迹帧级诊断单独统计，不能混用分母。
6. 按业务方向配置，不符合方向的候选可审计地拒绝，异常比例仅作告警。允许双向、单向、掉头、短时间多个真实相邻目标。对端点和速度的任何全局阈值修改，须同时通过漏计和误计回放；不能只看拒绝数下降或事件数上涨。

### 4.4 去重、落盘和事件契约

**两层去重必须分开：**

- 视觉/业务层：同一设备、同一配置版本和流会话内的同一可靠轨迹、同一越线确认，只创建一个候选及事件；同一轨迹再次真实跨线依据侧别状态、方向、时间和轨迹证据生成新候选。空间距离和时间窗只对可靠的同轨迹重复确认辅助判断；不同目标或不同轨迹不能仅因同点同秒而丢弃，重连或 ID 改变不能假装稳定轨迹 ID 一定对应同一物理对象。模糊关联保留证据并人工复核，不自动吞计数。
- 传输/存储层：事件第一次形成后生成不可变 `event_id`，与规范化 payload、候选证据及配置版本一起持久化，重试和重放保持同一 ID；相同 ID、相同内容只能应用一次并返回相同确认，相同 ID、不同内容返回冲突并报警。不同 ID 即使时间相近也不能在存储层自动合并为一个人/车。

事件至少包含 `event_id、candidate_id、device_id、stream_epoch、line_id、line_config_version、model/tracker_version、event_type、class、direction、track_id（含会话命名空间）、cross_point、coordinate_basis、occurred_at（带时区及来源/可信度）、receive_at、confidence、decision/replay_id`。必要时保存画面片段索引和保护后的证据引用；规范 JSON 及签名/摘要，检查设备存在、类别方向合法、时间有效、坐标有限、版本可查。

现状中 `counter.process_tracks` 会先更新内存去重状态，随后 `pipeline.py` 才写 SQLite；崩溃发生在两者之间可能出现未持久化的候选，当前队列无法恢复未入队事件。SQLite 队列已实现同 ID 内容冲突检查、按设备排序、失败重试；但成功投递会删除队列行，且发送 payload 只有事件 ID、设备、类型、时间，完整轨迹证据不能从后端重建。

改造应做到：

1. 在单路处理边界把确认状态、候选、完整事件及发送队列写进**同一可恢复本地事务**，提交后才把该事件视为已确认；故障后从本地日志重建待发送状态。事务前突然断电导致尚未形成的视觉事件仍依赖录像重放，不能声称已保证真实过线零漏。
2. 本地队列放在持久卷，核实 WAL、同步模式、备份恢复、磁盘水位和容量；满盘或提交失败时暂停该路确认、明确记录缺口并报警，不可吞异常后继续显示健康。队列重试、网络超时、后端 5xx/429 指数退避；永久 4xx/ID 冲突进入隔离队列，附原因与人工处理，不阻塞其他设备且不得悄悄删除。
3. 服务端以可恢复的权威事件明细账本为最终事实源：建议在 MySQL 事务中唯一写入事件、业务变更及投递/物化任务，再返回含 `event_id、payload_hash、accepted/applied` 的确认；Redis 作为可重建的实时物化。不得假设 Redis 和 MySQL 的两个独立写入自动构成跨库事务。评估现有 Redis 原子 Lua 迁移、旧客户端无 ID 的兼容期、版本协商、失败回退、容量、备份和恢复；新 AI 客户端必须带 ID。完整账本及发送历史的保留期应覆盖重放和对账期限。
4. 对已确认事件做到幂等重试、进程或主机故障后恢复；提交前、确认后/本地删除前、局部物化失败、Redis 重启/内存不足、MySQL 不可用、ACK 丢失都要注入验证。用本地队列的存储错误和最老待投递时间判断健康；日志 `outbox丢弃=0` 是现有帧管道其他 outbox 指标，不能当作持久事件队列无丢失的证明。
5. 当前后端的幂等记录在 Redis 中永久累积，事件展示列表仅保留 2,000 条，不能替代持久明细账；Redis 脚本也不是跨系统的持久事务。对容量、淘汰策略、恢复以及 ID 保留期限给出方案，幂等期限不得短于最长重试/回放期限。

### 4.5 累计、迟到、当前值和对账

- 统一用带时区的 `occurred_at` 归属业务日/小时，并存储 UTC 与业务时区；所有日志、库、回放及报表采用同一事件时间、窗口 `[start,end)`、事件口径和配置版本。接收时间只用于监控和排序辅助。
- 事件按设备、线、类别、方向、小时形成事实明细。小时桶和日桶是事实明细的物化结果；迟到、重放、补偿事件按原发生时间标记桶版本并重算。若原小时数据不完整或超过保留期，隔离并人工审核，不能用局部数据覆盖完整归档。记录归档水位和版本，核对 MySQL 前确保该桶已稳定；异常桶不得标为已完成。
- 当前代码对全局当前人数/车辆数做零下限钳位，而设备当前值直接增减；迟到或乱序下“先出后进”可能与“先进后出”得出不同当前值，也不能保证全局等于设备求和。定义初始盘点值、区域边界、事件顺序和补偿规则；对确定完整闭合边界，可按 `初始值 + 已确认进入 - 已确认离开 + 经审核补偿` 重算；缺少初值、遗漏入口或有未恢复缺口时显示未知/不完整而非伪精确数字。若展示层需非负，保留原始差额及异常，不能丢弃账务信息。
- 分层每日对账（小时级滚动检查）：①候选数＝明确接受＋明确拒绝＋待确认/异常；②在同一生产者和水位下，以 `event_id + payload_hash` 比较本地已持久集合 C、权威账本已接收集合 B 和本地待投递/隔离集合 P：C−B 必须仍在 P，B∩P 则可能是 ACK 丢失后的待重试，不能重复相加；③权威明细按同一水位/版本聚合＝Redis 设备、全局、小时/日物化＝MySQL 对应已完成小时；④对真实视频做一对一对象级抽检。各项需区分未到水位、迟到、重试、隔离、重复、错设备/方向和不可恢复缺口。
- 发现差异时冻结受影响版本的“已完成”状态，保留原始事件、轨迹、录像、配置和计算版本；人工核因后，补发原 ID 或以可追溯的冲正/补偿事件修复，记录操作人和原因，重算并再次对账。禁止直接改累计值后掩盖差异；无录像真值时明确标记无法证实而非自动补数。

### 4.6 性能与质量可观测

- 以单路和全引擎两个层次报告：源接收、采样、覆盖、提交、排队、预处理、唯一批次推理、后处理、跟踪、判线、落盘、ACK、归档；保存每项样本数、均值与统一直方图 P50/P95/P99、队列深度、最长帧间隔，以及实际数据覆盖。按设备配置版本和 `stream_epoch` 切分，避免跨热更新混算。
- 拥堵上报/视频质量检测、事件循环、GPU 空闲/计算、CPU 解码与颜色转换分别测量；GPU 原始采样同时记录时间、设备、容器/进程、利用率、显存和采样周期。单一 `nvidia-smi` 利用率不能证明空转根因。异常质量监控的失败、黑屏、冻结也要可见，不依赖“无异常日志”。
- 先固定 1080P、真实路数、摄像头类型、码率/编码和同一配置及模型；分别实验 FFmpeg 修复、组批窗口、采样和模型输入尺寸，每次只改变一个因素并保留回滚版本。采样帧率、均批和处理率与人工标注准确率一起评估；双引擎或流水线仅在确认模型线程安全、每路结果有序、不超显存且 A/B 效益明确后引入。不要以降低采样或停路制造低丢帧率的假健康。

#### 4.6.1 GPU 利用率不高时的优化路径

现场 GPU 利用率不超过 40% 是用户已确认的运行观察，作为本方案的现场现象；目前缺少与各路统计对齐的采样区间、设备和进程明细，不能据此断定 GPU 等待的唯一原因，也不能把利用率高低本身当成计数准确率。10 月 28 日的 26 路数据作为历史参照：平均处理 3.651 FPS、采样后加权丢帧约 43%、均批 24.683、推理 182.347 ms/批、跟踪 2.156 ms/帧。这些是设备窗口汇总，并非当前运行实例的逐批性能测量。

| 顺序 | 要做的实验 | 需要确认的条件及风险 |
|---|---|---|
| 1. 获取当前基线 | 同期持续采集每秒 GPU 利用率和显存、CPU/线程使用、各路实际解码后端与 FPS、采样后丢帧、最大帧间隔、组批/执行器等待、推理与跟踪时间；保存在线设备数、镜像、配置、模型和流参数。 | GPU 利用率表示采样期内 GPU 活跃程度，不能单独判断模型吞吐或端到端性能；与历史日志不可混为一组。 |
| 2. 保障视频供给 | 检查当前实例是否仍有 `fps_mode` 失败和 OpenCV 回退；若存在，先在部署镜像修复并验证 FFmpeg 能力，再对比解码、缩放和帧率。修复 WVP 不可用通道，避免无输入时追求 GPU 利用率。 | 10 月 28 日的回退已证实，但当前是否仍然发生需要实测。解码后缩放至 960×540 可能影响远景小目标，必须与原尺寸做真值比较；FFmpeg 选帧也不保证减少原始帧解码开销。 |
| 3. 分离推理与跟踪 | 当前 `GpuInferEngine` 使用一个推理线程，`_run_batch` 在 `predict` 后逐路运行 `_tracks_for`，所有轨迹处理完成后该线程才处理下一批。增加引擎级逐批计时；若跟踪占用确实形成等待，试验模型预测线程与按设备串行的跟踪工作线程分离。 | 预测完成后先安全复制跟踪所需的检测数据到独立 CPU 内存，限制队列和在途量；按设备顺序处理，检查流代次、取消及重连，防止旧帧或乱序污染跟踪。先保持每设备最多一个未完成请求，再比较 FPS、帧间隔、漏计和误计；不得无界堆帧。 |
| 4. 测试尺寸与组批 | 以同一组标注视频，单变量比较 `imgsz=960` 与 `640`，以及不同组批等待窗口；实际记录模型输入、批次分布和目标尺寸。 | 小尺寸可能降低远景小目标召回；更短组批窗口可能使批变小、总吞吐下降。当前配置已请求 GPU FP16，不应把“开启 FP16”当成新增收益。GPU 利用率即使下降，只要实际吞吐与计数真值更好也可以接受。 |
| 5. 测试双引擎 | 保留原方案的双引擎，完成最低限度的基线打点后，在隔离环境按第 1.1 节比较单/双引擎与 960/640 组合；可与其他候选分别开展，不要求先完成全部链路改造。 | 两引擎会增加模型/显存占用并可能互相争抢；须验证线程安全、内存、单路公平性、每路顺序以及真实目标准确率，效果不稳定则回退。 |

阶段之间应保持线上统计口径、摄像头流量、线和模型版本可比，先单路或影子环境、再逐级扩路。可用现有 `scripts/zbny-bench-gpu-infer.py` 在隔离或维护窗口测量合成输入的推理上限：该脚本会加载额外模型并占用 GPU，不能在正常生产负载上直接运行；合成结果也不能作为真实视频准确率证明。实验采用第 7 节的覆盖、帧率、真值和对账门槛，并与同设备同视频的旧版本对照；不能承诺“GPU 提到某个百分比就一定少漏计”。

#### 4.6.2 将现场低利用率转化为可验证的瓶颈判断

`nvidia-smi` 的 GPU utilization 是采样期间 GPU 有一个或多个计算内核运行的时间比例，并不直接表示计算单元占用率，也不能把 40% 自动换算为可用吞吐余量；它还可能反映该 GPU 上其他进程。采样窗口长度因设备而异，逐秒查询与真实推理时间线需要对齐。详见 [NVIDIA 的利用率定义](https://docs.nvidia.com/deploy/nvidia-smi/index.html)。

先在**不加载额外模型、不改变生产配置**的情况下记录至少 30 分钟当前数据：GPU 型号、驱动、每秒利用率/显存/功率、其他占卡进程；同期在线设备数、每路实际源/输出尺寸和解码器、采样/处理帧率、帧间隔和丢帧、每个引擎的批次分布与队列。`/health` 的 `batch_sizes` 是累计直方图，应用区间前后的差值计算该区间批次；`shapes` 是带 TTL 的形状集合大小，不能当作瞬时每组流数。按设备区分无帧、低帧、推理排队、存储暂停等状态。

增加引擎级**每批唯一 ID**及以下时间点：最早帧接收、入队、派发、单线程开始、`predict` 前后、检测结果转 CPU、各路跟踪完成、整个批次完成。记录批大小、实际模型输入形状、各阶段耗时、每路结果状态、代次/排队过期原因和处理帧间隔。使用采样式分析工具区分 GPU 工作、主机预处理/后处理及设备同步，避免在生产每批强制全局同步造成额外等待；性能分析工具本身的开销应单独测量。

| 同期观测 | 下一步判断 | 不应直接得出的结论 |
|---|---|---|
| GPU 低，待处理队列经常为空，解码/采样或 WVP 有缺口 | 查各路首末帧、FFmpeg 回退、读取线程、图像转换和网络，确认 GPU 是否缺少可用输入 | 不能因 GPU 空闲就加模型实例 |
| GPU 低，批次已就绪但推理线程被转 CPU、跟踪或其他主机处理占用 | 对比每批 `predict`、数据转移、逐路跟踪及下一批开始时间，验证是否可重叠 | 不能把设备窗口的平均 `跟踪 ms/帧` 直接当作真实逐批关键路径 |
| `predict` 墙钟较长，但 GPU 内核运行占比低 | 分解模型输入准备、CPU 到 GPU 传输、GPU 计算、后处理与同步，检查线程争用和小任务调度 | 现有 `推理 ms/批` 不能等同于纯 GPU 核函数耗时 |
| 当前同时存在多种输出形状，分组批次较小且经常超时 | 按形状统计设备及实际批大小；结合帧龄比较等比缩放/填充等候选方案 | 同为 1080P 源流不保证解码输出形状相同；历史日志均批接近 25，也不足以证明当时存在组批碎片 |
| 每路输入正常、GPU 计算饱和或显存/带宽受限 | 测试模型、输入尺寸及有条件的推理引擎加速 | 不再以提高利用率为目标；必须比较真实吞吐和真值 |

当前代码中 `predict` 与逐路 `_tracks_for` 在同一个单线程执行；`INFER_QUEUE_MAX_BATCHES` 即使大于 1，也只是限制在途/排队批数，不会把该线程变成多个并行的 GPU 推理工作线程。`_tracks_for` 对非空结果分别执行 `xyxy.cpu()`、`conf.cpu()`、`cls.cpu()`；现有 `跟踪 ms/帧` 包含这些数据转移/潜在同步及跟踪计算，不能简单称为纯 CPU 跟踪时间。

容量估算可用于确定实验目标：以历史日志涉及的 26 台为示例，假设同时在线 26 路、每路要求 6 FPS、稳定每批 25 帧、只有一个串行推理工作线程，需处理约 156 帧/秒，平均每批可用时间约 `25 / 156 = 160 ms`。10 月 28 日日志的 `predict` 约 182 ms/批是按设备窗口统计的历史值，口径与假设不完全相同，并且后面还有逐路处理；因此它只能提示需要测量真实引擎批间隔，**不能以此断言当前容量上限或承诺 6 FPS**。实际 32 路的估算见第 4.6.5 节，第 7 节仍以真实逐路数据和计数真值验收。

#### 4.6.3 新增的优化候选和保护条件

1. **减少 GPU→CPU 数据搬运和同步**：在隔离环境比较现有每路多次取回与合并取回检测框、置信度和类别，再按原始批次顺序拆分。计时包括准备、拷贝及同步，不能只看单个 API 调用；目标为减少实际批间隔。非空/空结果、不同结果布局、不同目标数、类别/坐标/置信度及批内设备对应关系都必须与旧路径一致；空检测仍要推进对应 tracker。此项是候选，收益由实测决定。
2. **推理与跟踪流水化**：若阶段打点证实批次被逐路跟踪阻塞，模型调用保持单线程；将安全复制后的检测结果分发到有界的设备跟踪工作队列，各设备内部严格串行。第一阶段仍保持每设备最多一个未完成请求，保留批次结果数量检查、超时、取消、设备代次及重连保护；连续多设备、高密度结果和慢 tracker 下不允许结果错路、乱序或无界积压。并发线程数在 1/2/4 等配置下按 CPU 实测，不假定 Python 或第三方库一定能并行获益。
3. **按实际形状和帧龄调度**：保留同尺寸组批并统计各组的吞吐、等待和最老帧年龄；优先试验合理的批大小/等待窗口与设备公平性。只有现场证实形状碎片时才测试统一画布，保留原始 1920×1080 坐标基准和准确的缩放/填充还原；不同裁剪、画幅或小目标场景单独验证。不得通过增大队列上限、等待更老的帧或丢弃慢设备来制造高利用率。
4. **模型执行引擎作为后续选项**：如果已排除供帧和主机串行开销，仍需提高吞吐，可在目标 GPU、驱动、镜像及模型版本固定的隔离环境评估 TensorRT/FP16 等部署方式。动态批量必须覆盖实际最小、典型和最大批次，输入形状、预处理、NMS、类别和输出坐标保持兼容；转换、冷启动、显存、实际端到端耗时及数值偏差均需验证。现有项目默认请求 FP16，不能将其本身视为新增优化。TensorRT 的动态形状需要按输入范围建立优化配置，且不同批量需要实测，参见 [NVIDIA 动态形状说明](https://docs.nvidia.com/deeplearning/tensorrt/latest/inference-library/dynamic-shapes-basics.html)及[性能优化说明](https://docs.nvidia.com/deeplearning/tensorrt/latest/performance/optimization.html)。
5. **保留非 GPU 计数问题的独立闭环**：WVP 断流、摄像头线/锚点方向、轨迹断裂、持久化及幂等对账等问题不随 GPU 利用率提高自动消失；按第 4.1–4.5 节分别处理。不能以事件数增加或轨迹拒绝次数下降代替人工真值。

#### 4.6.4 实验矩阵与放行判断

| 实验 | 不变条件和比较内容 | 成功与停止条件 |
|---|---|---|
| 基线 | 同一硬件、镜像、模型、1080P 源、设备数量、配置与输入视频；采集 ≥30 分钟同期数据 | 每路采样/处理 FPS、最长间隔、丢帧和引擎真实批间隔可解释；离线或异常时段单独标记 |
| A：解码/供帧 | 仅改变 FFmpeg 兼容或已验证的解码输出尺寸 | 各路覆盖、帧间隔与有效 FPS 改善或持平；小目标及方向真值不退化 |
| B：结果拷贝 | 仅改变检测结果搬运，固定模型和 tracker | 空/非空、不同设备及重连下，检测和事件与基线逐项等价；真实吞吐改善且无错路 |
| C：推理/跟踪分离 | 固定解码、模型及搬运方式，对比工作线程数和有界队列 | 每路有序、不串设备、无饥饿/旧代结果；尾部延迟、GPU 间隔及帧率改善，事件精度不退化 |
| D：输入、批次或可选引擎 | 每次只改变一个候选，比较性能和同一标注视频 | 人/车、进/出、远景和遮挡等按第 7 节评估；漏计或误计不达标即停止，不能用高 GPU 利用率抵消 |

模型耗时微基准先用合成帧定位引擎上界，再用**真实帧及目标密度**复测；不同路数逐级验证容量和公平性，不能把随机空画面的结果当现场吞吐。算法 A/B 使用同一原始视频和时间戳、同一线及配置版本，影子运行须使用独立队列和统计库，避免向生产重复写事件。每次实验保留指标、配置、日志、视频/标注版本、差异事件和回滚条件；通过第 7 节才可进入逐路灰度。

#### 4.6.5 单卡 NVIDIA T4、32 核 CPU 的参数调整建议

现场提供的资源观察：一张 NVIDIA T4，可用显存 15,380 MiB、已用 2,412 MiB，GPU 利用率约 39%，32 核 CPU 使用率约 35%；用户称多次日志测试基本一致。按该读数计算显存尚余约 12,968 MiB。该数据适合作为双引擎试验依据，但不是双引擎峰值显存、当前各路有效处理率或真值准确率的证明。NVIDIA 将 GPU utilization 定义为采样期间至少有一个 GPU 内核运行的时间占比，不能把 39% 直接换算为仍有 61% 的吞吐余量；T4 支持 FP16。参见 [NVIDIA SMI 指标说明](https://docs.nvidia.com/deploy/nvidia-smi/index.html)和 [T4 产品规格](https://www.nvidia.com/content/dam/en-zz/Solutions/Data-Center/tesla-t4/t4-tensor-core-datasheet.pdf)。

现场确认实际共有 **32 路 1080P**，本节按 32 路全部同时在线设计单卡 T4 的容量试验。10 月 28 日日志中有统计记录的业务设备为 26 台，属于历史观察，与 32 路视频可能不是同一口径；须按业务设备、GB 设备和通道逐一匹配完整的 32 路权威名单，确认哪些视频或时段未被日志覆盖，不能直接把数值差认定为掉线或漏计。优先验证下面的**双引擎候选组合**；这些值只构成试验目标，先用现场当前真实值建立基线。

| 参数 | 建议试验值 | 修改或核对的位置 | 作用和边界 |
|---|---:|---|---|
| `INFER_MODE` | `gpu_batch` | 部署机项目根目录 `.env.gpu` | 显式 GPU 模式自检失败会进入 `unavailable`，须监控并回退。 |
| `INFER_ENGINES_PER_GPU` | `2` | 部署机项目根目录 `.env.gpu` | 每卡两个模型实例和工作线程；不保证 GPU 内核并发或吞吐翻倍。 |
| `INFER_SLOTS_PER_GPU` | `0` | 部署机项目根目录 `.env.gpu` | 自动按总容量分配槽位。 |
| `INFER_CAPACITY` | `32` | 部署机项目根目录 `.env.gpu` | 单卡双引擎自动分配为各 16 槽；32 路在线时无额外接入槽位。 |
| `INFER_SLOTS_MAX` | `32` | 部署机项目根目录 `.env.gpu` | 每个自动分配引擎的槽位上限；本组计算为 16，不触及上限。 |
| `INFER_HALF` | `true` | 部署机项目根目录 `.env.gpu` | GPU FP16；属于现有能力。 |
| `INFER_BATCH_TIMEOUT_MS` | `40` | 部署机项目根目录 `.env.gpu` | 组批窗口；应与 80 ms 对比批次、处理率和精度。 |
| `INFER_QUEUE_MAX_BATCHES` | `2` | 部署机项目根目录 `.env.gpu` | 保持有界调度。 |
| `INFER_MAX_QUEUE_AGE_S` | `2` | 部署机项目根目录 `.env.gpu` | 请求开始推理前的等待期限，不是端到端完成时间上限。 |
| `DECODE_BACKEND` | `ffmpeg` | 部署机项目根目录 `.env.gpu` | 核查每路实际未回退 OpenCV。 |
| `DECODE_MAX_SHORT_SIDE` | `540` | 部署机项目根目录 `.env.gpu` | 1080P 流输出 960×540。 |
| `DECODE_FPS_SAMPLING` | `grid` | 部署机项目根目录 `.env.gpu` | 按源 PTS 选帧；缺少源 PTS 时保留输入帧，必须监测实际帧率。 |
| `inference.imgsz` | `960` | [configs/business_rules.yaml](../configs/business_rules.yaml) 的 `inference` 段 | 按批次生效，覆盖环境变量 `INFER_IMGSZ`。 |
| `inference.decode_max_fps` | `8.0` | [configs/business_rules.yaml](../configs/business_rules.yaml) 的 `inference` 段 | 新建或重连流生效，覆盖环境变量 `DECODE_MAX_FPS`。 |

工程上按业务 `device_id` 为新流分配槽位，优先选择设备数最少的可用引擎；32 路对应 32 个独立管道且都正常接入时预期 16 路/引擎，全部槽位占满。容量是接入上限，不是已经验证的吞吐承诺；槽位耗尽的新增设备返回 503，不自动创建独立模型。须核查业务设备、GB 通道与物理视频的映射及重连释放，避免同一物理视频重复注册、不同视频共用 ID，或正常设备因槽位未释放而无法恢复；不得通过放大槽位来掩盖重复注册。两个引擎各持有模型及单线程执行器，目前代码没有显式配置独立 CUDA stream。要核对运行日志及 `/health` 的两个引擎、槽位和各路分布，而不是把双线程视为 GPU 并行证明。引擎中的 `vram_mb` 是同一 CUDA 设备的进程分配量，双引擎时不能相加；以 `nvidia-smi` 观察全卡已用、峰值及其他进程。

32 路容量核算必须使用实际出帧而非配置值。假设 32 路每路实际采样均为 8 FPS，则合计为 **256 采样帧/秒**；保持每路采样后丢帧率不高于第 7 节的 10%，意味着总有效处理量约需达到 **230.4 帧/秒**，且仍须逐设备达标。若只达到每路 5 FPS，则合计 160 帧/秒，在实际采样为 8 FPS 的条件下仍会约丢失 37.5% 的采样帧，不能仅凭 5 FPS 判定达到完整性能门槛。以上是稳定同帧率条件下的估算，实际以逐路时间窗口的采样和处理数为准。

若两个引擎各分配 16 路、每批恰好完成 16 帧，则每引擎需要约 128 有效帧/秒才覆盖每路 8 FPS，相当于完成批次的间隔平均约 125 ms；该间隔受输入等待、推理、逐路跟踪及两引擎竞争共同影响，并要求共享的单张 T4 同时能支撑两个引擎的总负载。实际批次不足 16 时所需批间隔更短，因此应记录真实批次分布；不能把 10 月 28 日日志中 26 路下的平均批次或 `predict` 墙钟时间直接套用到当前 32 路。`/health` 中引擎 `batch_sizes` 是累计分布，区间差可估算送入模型的帧数，但其中可能含被取消或旧代请求，不等同于各设备的有效处理数；有效处理及最大间隔以各路统计为准。

实施和选择顺序：

1. 以完整 32 路名单核对业务 ID、GB 设备/通道、实际接入及日志覆盖，分 8、16、24、32 路逐级试验并最终在 32 路同时在线时采集至少 30 分钟基线；核验 32 个独立管道、每路 `source_is_1080p=true` 和实际解码后端，以及双引擎的设备/槽位分布。记录逐路采样及处理 FPS、采样后覆盖丢帧、最大处理间隔、批次大小、组批/执行器/推理/跟踪耗时、显存和逐核 CPU。先排查流未接入、FFmpeg 回退及 WVP 缺口；影子试验使用独立的事件和统计存储。
2. 以单引擎为对照，只改变为双引擎并校准自动槽位，使用相同视频及设备数比较；接着分别测试 `interval→grid` 和组批窗口 80 ms、40 ms。32 路拆成两个引擎后单引擎批次可能变小，40 ms 并不必然优于 80 ms，按逐路处理率、最大间隔及真值选择。记录每轮配置、引擎设备数、批次分布和资源曲线。上一轮生成的 `configs/1080p-count-accuracy-trial.env.example` 保留为单引擎对照文件，不会自动应用本节双引擎建议。
3. 固定录像及人工标注，对同设备、类别、方向进行一对一事件匹配，比较召回、误报和漏报；覆盖远景、夜间、端点、遮挡和高速目标。资源指标目标和 72 小时验收按第 7 节执行，GPU 利用率高低不作为独立放行条件。
4. 若双引擎后有效处理率不升反降、显存异常、设备饥饿、队列过期或精度下降，回退到试验前单引擎及原组批/采样参数；重建 AI 会产生空窗，保留 outbox 并记录缺口。`gpu_batch` 启动失败为 `unavailable`，应立即恢复已验证配置，而非等待自动降为 CPU。
5. 若远景小目标漏检仍明显且双引擎稳定，再**单独**对比 `DECODE_MAX_SHORT_SIDE=720` 与 `inference.imgsz=1280`（1080P 源输出 1280×720）；与 960×540 相比输出像素约增加 78%，模型实际输入及吞吐需实测。原方案的 `imgsz=640`、6 FPS 仍可作为容量对照，必须同时核对漏报与误报。

本方案不凭显存空闲直接扩张队列或启用 GPU 解码，也不更改计数线、方向、阈值和事件口径。现场录制的资源利用率来自用户报告，本工作区未连接该 T4 服务器进行实测。

#### 4.6.6 参数文件和生效方式

以下是按当前工作区实现的**试验参数位置**，不是现场当前实配。部署机使用 [scripts/start_all_gpu.sh](../scripts/start_all_gpu.sh) 时，该脚本读取**部署机项目根目录的 `.env.gpu`**；本工作区没有这个现场文件。它包含其他部署配置，应只更新或新增以下键，保留原有键及密钥，不要用本片段覆盖整个文件：

```dotenv
INFER_MODE=gpu_batch
INFER_ENGINES_PER_GPU=2
INFER_SLOTS_PER_GPU=0
INFER_CAPACITY=32
INFER_SLOTS_MAX=32
INFER_HALF=true
INFER_BATCH_TIMEOUT_MS=40
INFER_QUEUE_MAX_BATCHES=2
INFER_MAX_QUEUE_AGE_S=2
DECODE_BACKEND=ffmpeg
DECODE_MAX_SHORT_SIDE=540
DECODE_FPS_SAMPLING=grid
# 以下为 YAML 不含对应项时的回退值；当前 YAML 仍有更高优先级。
INFER_IMGSZ=960
DECODE_MAX_FPS=8
```

同一项目下 [configs/business_rules.yaml](../configs/business_rules.yaml) 中检查并修改已有 `inference` 段，不要再创建第二个同名段。工作区目前已是下列值，现场须另行核实：

```yaml
inference:
  imgsz: 960
  decode_max_fps: 8.0
```

- YAML 的 `inference.imgsz` 覆盖 `.env.gpu` 的 `INFER_IMGSZ`；`inference.decode_max_fps` 覆盖 `.env.gpu` 的 `DECODE_MAX_FPS`。仅改环境变量而不核查 YAML，可能没有预期效果。`imgsz` 按批次热重载，`decode_max_fps` 对新建或重连的流生效；因此直接编辑被运行中服务挂载的 YAML 会影响现网，应在隔离环境或安排好的变更时段操作。
- GPU Compose 的变量转发和缺省值位于 [docker-compose.gpu.yml](../docker-compose.gpu.yml) 的 `services.ai.environment`。这些缺省值不是现场 `.env.gpu` 的真实内容；运行 Compose 时当前 shell 中同名已导出变量也可能覆盖 env 文件。结构性环境参数在 AI 容器及推理引擎启动时读取，变更后须按现场流程重建 AI 容器，记录中断及重连缺口。
- 上一轮的 [configs/1080p-count-accuracy-trial.env.example](../configs/1080p-count-accuracy-trial.env.example) 明确设置 `INFER_ENGINES_PER_GPU=1`，是**单引擎对照**。如果它作为后一个 `--env-file` 加载，会把 `.env.gpu` 的双引擎值覆盖为 1；不可误当作本节双引擎配置。
- 远景试验涉及两个文件：`.env.gpu` 改 `DECODE_MAX_SHORT_SIDE=720`，`configs/business_rules.yaml` 改 `inference.imgsz: 1280`；恢复前值同样分别在两处操作。640 输入对照改 YAML 的 `inference.imgsz`，6 FPS 对照改 YAML 的 `inference.decode_max_fps`。这些是单独实验，不与首次双引擎试验同时改动。
- 越线参数位于 `configs/business_rules.yaml` 的 `counting` 段，检测置信度位于同文件 `tracking.yolo_conf`，跟踪器参数位于 [configs/bytetrack.yaml](../configs/bytetrack.yaml)；本组 T4 试验不要求调整它们。保持事件协议、设备线、方向和 ROI 现值。
- 重建后查看 `/health` 的 `effective_config`、`infer.mode`、各引擎 `batch_timeout_ms` 与槽位；在 `/devices` 核对 32 路实际后端、源/输出尺寸、处理 FPS 和帧间隔。`effective_config` 中标为 `next_connection` 的值不是旧连接的实际值；实际后端以各路为准。容器内环境变量只查看上述无密钥参数，避免输出完整环境。

### 6.1 本次审核已做的验证

## 7. 上线校验、监控与回退标准

以下数字是本次建议的**验收门槛**，需要在固定场景和业务口径下执行；资源和 FPS 指标不能替代准确性。业务如要求更高，应书面约定后以更高标准为准。

1. **真值数据集**：对实际 32 路逐路确认线、方向、ROI、拓扑和画面，并核对其与历史日志的对应关系；重点覆盖历史日志中 6 台零事件、216012 端点、3496 高“夹角”设备及 WVP 失败相关设备。取得白天/夜间、不同天气与光照、拥挤/遮挡、相邻目标、低速/高速、进/出和掉头片段。人工按设备、目标、类别、方向、越线时间和是否有效标注；由第二人复核样本与分歧，保存视频哈希、起止、配置和标注版本。无录像或未建立真值的设备标记“未验收”。
2. **精度**：以同设备/线/类别/方向的真值事件和预测事件，按预先固定的时间容差做一对一最优匹配；分别计算人流和车流 Precision=TP/(TP+FP)、Recall=TP/(TP+FN)，各≥95%；各自进/出及总数相对误差 `|预测-真值|/真值` ≤5%。真值为 0 时禁止除零，报告误报数量和对应视频；每类整体至少 200 个有效真值事件且每方向至少 30 个，未达到的方向或场景标为样本不足，不得宣布通过。每设备/方向达到 30 个样本时单独要求 Precision、Recall 均≥90%；其他设备列待补样。对 6 台零事件设备必须分别取得有真实通过的验证片段，或书面确认其业务上确无目标且状态可观测；不能以空片段证明无漏计。相邻目标、端点、遮挡、掉头、重连和配置切换每类至少覆盖 30 个标注事件；样本不足的场景不得通过。
3. **覆盖与性能**：按设备应在线时间为分母，连续 72 小时各设备可用处理覆盖≥99.9%；按应在线时段内全部完整 30 秒窗口统计，每设备≥99% 的窗口达到处理 FPS≥5，且每设备采样后加权丢帧率≤10%，同时记录最大处理间隔及端到端分布。无帧、低帧和故障窗口均纳入分母；提前批准并登记的计划维护按业务约定单列，不得把事故追记为维护。该门槛仅是初始工程目标；任何采样改动都须通过第 2 项，不能通过减少采样或停用设备达标。所有缺口、回退、规则变更、满盘和 WVP 错误均须告警并可追溯。故障恢复期间应把实际缺口计入覆盖分母。
4. **一致性与恢复**：已持久提交事件在本地、后端事实账本和物化数据之间以 ID/摘要逐条核对，未关闭差异为 0；重复、重试和故障注入的已提交事件丢失数、重复应用数均为 0；迟到/隔离项有状态、负责人、处理时限。事件按小时/日、设备、方向对账一致且归档版本稳定；未形成事件但缺失的画面只可通过录像与真值补算，不能计入已保证部分。
5. **生产观察与回退**：每批灰度先影子对照再正式切换，比较同一视频和流量时段，记录配置、代码、模型、容量及缺口；连续 72 小时完整记录资源、准确性抽样、对账与告警。出现任一准确性下降、设备持续低帧、不可恢复缺口、事件丢失/重复、隔离堆积或对账不一致时，停止扩批、保留证据并回滚该设备/版本；恢复前状态标记为降级，禁止只凭 GPU 利用率或事件数上涨宣布上线成功。

### 7.1 上线后持续复核

每日检查预期在线设备覆盖、WVP/解码失败、队列 oldest age 与隔离数、完整小时对账差异、配置变更；定期抽取不同设备和光照视频复标，按设备/方向报告误计、漏计和未评估数量。建立问题单关联设备、缺口、事件 ID、录像、配置和处理人；对于当前日志中两条 480 通道，要先完成权威映射、网络/国标设备状态核查与恢复验证。

# 视频拉流与越线计数：审核及补充修复方案

审核日期：2026-10-28。范围：当前工作区代码、`2026-10-27.log` 和《AI调度与计数性能优化方案》。日志记录的是现场当时运行的版本，不应视为当前工作区代码已部署后的运行结果。本文是代码审查与修复计划，不代表已实施修复或完成现场验收。

## 一、结论

原方案的方向基本正确：共享模型、避免超容量逐路加载模型、缩短排队、核验子码流、监控有效帧率都值得做。但**目前不能直接按“已完成”部署验收**：当前组批实现存在可复现的事件循环卡死，背压、时间口径、事件可靠投递和设备健康判定仍不完整；性能与计数准确率均缺少现场对照证据。原方案中的容量和瓶颈结论应作为待验证假设。

实际链路是：WVP 点播并返回流地址 → AI 注册管道并异步启动 → FFmpeg/OpenCV 持续取帧、覆盖旧帧 → 批量推理和逐路 tracker → 轨迹、ROI 和越线判定 → WebSocket 和 outbox → 后端 Redis 计数。批量模式使用共享模型和逐路跟踪器；legacy 为每路独立模型。

## 三、现有方案逐项判断

1. **P0-1：必须返工后再部署。** 同形状聚合与限制 executor 在途批的方向合理，但当前实现有下述 P0 卡死问题；仅限制 `_queue.qsize()` 无法覆盖 collector 的 `pending` 和在途批。`_shape_target()` 首个设备出现时即为 1，可能首帧立即派发；设备下线后形状成员未立即清理，60 秒内仍会等待超时。80ms 不保证聚到指定批次，须压测延迟与吞吐。
2. **P0-2：有条件保留。** 对接近比例的画布缩放及逐轴坐标还原在几何上可行，但有检测精度影响，须用真实视频核验。`stream._ffmpeg_out_size` 对短边不大于目标的源直接返回原尺寸；16:9、4:3、其他比例及横竖屏也不一定同形状，因此不能声称 32 路必然同批。切换主/子码流后像素阈值也须重新标定。
3. **P1-1：拒绝超槽位回退方向正确，但不是就绪保证。** 批量模式满槽时返回 503 已有实现；引擎初始化失败仍可能整体回退 legacy。注册 201 只表示异步任务已启动，首帧、持续推理、事件投递均未确认。部分失败路径仍可能保留原 online 状态，应区分 WVP 在线与 AI 处理健康。
4. **P1-2：尚未真正解耦帧率。** `min_motion × 25` 只是以 25fps 为假设的阈值迁移，不保证与历史实际帧率行为等价；像素速度还依赖原始流分辨率。`traj_state.apply` 用当前一次 `dt` 反推缺失帧数，而不是累计该轨迹真实缺失时长；变帧率时仍会漂移。tracker 的 `track_buffer`、历史长度和 ID 切换速度仍含帧量纲。`counter.process_tracks` 对间隔 ≥10s 使用平滑旧值，并非截断到 10s。使用最近一次处理间隔判断两个轨迹点，而不是该目标两个观测点的时间间隔，遮挡/恢复时会错判。
5. **P2：可作为辅助，不能代替容量控制。** 跳帧并不减少 FFmpeg 已完成的解码，且每路同步跳帧不保证公平或延迟上界。业务规则降频、WS 节流和丢弃统计值得保留，但应检验热更新、连接断开和真实开销。低帧率告警只在成功处理帧后触发，完全无帧、卡死或重连时可能没有告警；outbox 丢弃是累计值，并不覆盖发送失败和 HTTP 错误。
6. **硬件和容量结论需撤回确定性表述。** 日志没有提供完整的逐阶段 CPU/GPU 利用率、FFmpeg 构建、编码格式和实测吞吐，无法确定解码一定是首要瓶颈或推理“不再是瓶颈”。T4/NVDEC 会话及吞吐依编码、分辨率、帧率、驱动、构建及同卡推理负载变化；不能仅以像素线性折算当作容量保证。子码流优先核验，但不是已证明的唯一可行路径。720p 的 CPU 核数、batch 32 耗时及单卡 32 路目标均待现场压测。
7. **配置和回滚需核验入口。** GPU compose 默认 80ms、槽位自适应；`app/common/config.py` 的直接启动默认仍为 40ms、8 槽，环境变量及业务规则覆盖后才是实际值。配置中 `decode_max_fps: 8.0` 可覆盖环境默认；需打印最终生效配置。`INFER_MODE=legacy` 会重新进入逐路模型竞争，不是 32 路满载安全回滚；回滚前必须先限流或分批停止并确认容量。

## 四、补充修复计划

### P0：阻断卡死、建立真正有界的调度

**问题 A：事件循环卡死，已隔离复现。** `gpu_engine._collector` 在有 pending、在途达到上限且 deadline 过期时，`timeout` 变为 0，持续执行 `get_nowait()` 且没有任何 `await`。推理线程完成后依赖事件循环执行的 `_on_done` 无法运行，`_inflight` 无法下降。用当前 `GpuInferEngine`、CPU 假推理 150ms、窗口 20ms、在途上限 1、两路异步提交复现：外层 5 秒 `timeout` 退出码 124，内部 1 秒 asyncio 超时也无法执行。该验证不使用真实 GPU，不代表日志现场已经触发了同一缺陷。

修复要求：

- 用事件/条件通知批完成，或采用确保会让出事件循环的等待；在途已满时不能因过期 deadline 自旋。完成、异常、取消、关闭均唤醒调度器；不能通过同步 sleep 阻塞事件循环。
- 建立全链路上限：按设备限制待处理请求，统计 queue + pending + 在途，不只看 queue；同设备最多一个排队请求，较新帧替换较旧帧，并完成被替换 future，保证各路公平。每批有独立最大帧数和显存上限，超限分批，避免 pending 一次性变成无界大批。
- 对每帧定义最大排队年龄，过期或取消时从调度集合清除且不再更新 tracker；跟踪器每路结果按采集顺序提交，设备解绑/重连使用代际标识，丢弃旧代结果。关闭时完成或失败所有 future，不能遗留等待者。
- 增加按真实批次计数的批大小分布、shape 数、pending/在途、过期/替换/忙丢帧和各路连续无服务时长。实测后再确定组批窗口，不能以均批数字代替吞吐、公平性和延迟。

**问题 B：等待指标不准确。** `gpu_engine._run_batch` 在 `predict()` 结束后取 `done_at` 计算 `wait_ms = done_at - enqueued_at`，包含排队、执行器等待和模型预测；`infer_ms` 也另行记录。应记录采集/接收、入队、组批派发、执行器开始、预测结束、tracker 完成、事件接收/落库等时间点，分别输出组批等待、执行器等待、推理、跟踪、总耗时及 P50/P95/P99。先统一命名，再比较新旧指标；各设备均批是逐帧加权，另需引擎级按批统计。

### P0：分离存活与业务健康

- 保留 WVP/摄像头在线状态，另设 AI 状态：注册、拉流中、首帧、推理中、降级/故障及最近成功处理/事件投递时间。201 表示已受理，不能当作首帧就绪。明确启动失败与容量满时的状态更新、重试和恢复，覆盖手动启动与自动同步路径。
- 用独立 watchdog 定期检查最近读帧、最近成功推理和事件循环延迟；没有帧、推理永不完成或重连也能告警。以 30 秒滑动窗口观察有效 FPS，同时记录最大帧间隔和缺帧持续时间；若事件循环本身卡死，还需进程外健康探针。
- 排查 FFmpeg/OpenCV 连接仍存活但长期不出帧的情况，设置基于最后新帧时刻的超时和有限重连退避；连接变化时明确重置 tracker、轨迹、计数状态及时间基准，避免断流前后误缝合和 ID 重用。

### P1：计数时间与事件投递

- 在 `FramePacket` 记录可用的源 PTS/采集时间和本机单调接收时间，贯穿推理、tracker 和 counter。没有可信源时间时显式标注“接收时间”，不能伪装为相机拍摄时间。每个轨迹点保存时间戳，速度和缺失/缝合窗口按该轨迹相邻观测的实际时间计算；超长间隔按失联处理，不以 EMA 代替真实间隔。停止/重连、异常跳变与乱序须有明确策略。
- 审查 `track_buffer`、历史点数、`hold_frames`、ID 切换阈值与基准帧率；选择统一时间语义或在限定帧率下明确标定，检查空检测帧时 tracker 是否需要推进。低帧率会增加跨越未观测区间，时间换算本身无法保证准确率。
- 以跨线发生时间或可解释的插值时间作为事件时间；目前 `EventGenerator.generate` 使用确认时 `datetime.now()`，排队/滞留和跨小时情况下可能归入错误时间窗口。保留确认时间以便审计。
- 当前 `_outbox_put` 满时可丢事件，`_push` 对 HTTP 非 2xx 只记录状态且不重试，网络异常也吞掉；重启和 sender 取消可能丢内存消息。先为越线事件引入稳定 `event_id`、持久化 outbox、失败重试及告警；快照类消息可合并覆盖。后端必须在**同一原子操作/事务**内完成去重和计数更新，去重保留期覆盖最大重试期，再启用重试；验证请求已提交但响应丢失、服务重启、队列满和存储不可用。历史累计及时间窗口 TTL 的补偿策略需明确。不能只新增重试，否则会重复计数。

### P1：核验源流和计数配置

- 在后台记录请求的主/子流类型、WVP 版本与响应中可用的通道/流标识、AI 实际 URL 的脱敏标识、codec、分辨率、帧率；对同一设备分别核对相机配置、WVP 主子流映射、点播返回和 ZLM/AI 实际流，确认调用是否支持 `streamType=sub` 及现有流是否复用。不能仅凭 `WVP_STREAM_SUB=true` 推断现场配置故障。
- 子码流方案要验证小目标识别、计数线/ROI 坐标映射、相机画幅/裁剪变化及像素速度阈值；如子码流裁剪、视角不同或分辨率变化，需重新标定，而非直接沿用主码流像素参数。流地址和设备标识出日志时注意脱敏。
- 先测实际 `ffmpeg -hwaccels`、`-decoders`、驱动和容器可用性，再分别比较 CPU、NVDEC 和可用子码流。记录完整编码、分辨率、码率、源帧率、取帧率、资源占用、GPU 推理及准确率，选择能通过验收的组合，不预设单一路径。

## 五、实施顺序与验收

1. **本地回归门槛**：先修 P0 调度卡死，以受控慢推理重放上面的两路场景；验证事件循环心跳、全部 future 结束、在途恢复和正常关闭。增加混合 shape、超时、并发超载、取消、设备卸载/重连、空检测和批推理异常用例；检查有限内存、无同路乱序/旧代结果、无饥饿。当前仓库 `tests/` 未发现已跟踪测试源文件，原文所列合成结果尚无可复核的测试文件与输出，本次未独立复现其全部用例。
2. **计数回放门槛**：固定标注视频及配置，逐目标逐方向比对事件，覆盖快/慢车、遮挡、ID 切换、正反方向、边界、ROI、不同码流及分辨率、变帧率、长断流和跨小时。报告人工真值、漏计、误计、重复计数、方向错误，以及事件时间偏差；精度阈值由业务确认，不能用“有事件”替代。
3. **现场容量门槛**：记录版本、配置、镜像、硬件、视频源和网络条件；按 1、8、16、24、32 路逐级压测，同一台设备分别测独立解码、独立推理及端到端；最终负载至少连续运行 1 小时，并做断网/恢复测试。每路按固定 30 秒窗口报告 FPS、最大处理间隔、帧龄及端到端延迟 P95/P99、各类丢帧、事件投递成功与积压；同时记录 CPU、内存、GPU、显存、解码进程和各阶段耗时。目标为 32 路每路 ≥5 有效 FPS，是否长期稳定、所需批大小和延迟以实测为准。
4. **投递验收**：对照生成、持久化、发送、后端已应用数量及唯一 ID；模拟后端 5xx、超时、响应丢失、进程重启和存储满，验证不静默丢失、无重复累计、告警可见。无法持久化时明确标记计数不可信并报警。
5. **上线/回滚**：先小流量灰度，观察健康状态与人工计数；再逐级加路数。预先保存版本、最终配置和基线指标；回滚 legacy 前限流并验证资源容量。未通过 P0 和人工计数核验前，不将原方案中的性能或计数目标标为完成。

## 六、2026-10-28 修复和验证记录

本节记录当前工作区改动，不表示已经部署现场。上文是审核时的计划与风险描述；以本节和代码当前状态为准。

- **拉流**：帧记录本机解码接收的单调时间和墙钟时间，不当作相机采集时间；连续无新帧默认 15 秒重连（`STREAM_STALL_TIMEOUT_S` 可调，0 禁用）。流连接代次变化后重置该路跟踪和计数状态。修复 RTSP 的 FFmpeg/ffprobe 超时参数；OpenCV 由读线程自行释放，避免跨线程 release。抽帧由 `fps` 滤镜改为只选择原始帧，避免低帧率源被重复补帧而虚报处理帧率。真实本地模拟源的 RTSP、HTTP-FLV 在项目现有镜像内均以 FFmpeg 拉到帧并正常关闭；OpenCV RTSP 单独拉流和关闭正常。首次 RTSP 测试曾因 `rw_timeout` 不兼容回退 OpenCV，关闭退出码 139；修复后上述两条路径退出码均为 0。此验证不代表现场 WVP 子码流已开通。
- **推理调度**：修复过载自旋和旧代结果，限制每设备未完成请求及引擎总请求，支持过期、取消和停止清理；新增按批统计及等待拆分。引擎默认最大排队年龄 `INFER_MAX_QUEUE_AGE_S=2`，现场应结合丢帧、帧龄和准确率调整。真实 Ultralytics 的批量 tracker 使用逐路独立 ID；空检测帧也推进 tracker。批量引擎不可用时拒绝注册，不再自动进入 legacy；显式 legacy 为避免全局 ID 重置造成跨路混淆，当前仅允许单路。
- **计数与状态**：轨迹缺失、缝合和跨线速度使用目标实际观测间隔；超过 2.4 秒失联不推断跨间隔越线。事件时间按相邻帧本机接收时刻插值，仍受源端缓冲及本机时钟影响。设备心跳另带 `ai_status`，AI `/devices` 暴露处理健康状态；任务存在或设备在线不等于已有有效计数。连续无处理时 watchdog 告警，事件循环自身失活仍需进程外探针。
- **事件与统计**：同帧事件先写 SQLite 持久 outbox，再广播；后台只向声明原子幂等能力的后端投递，并按设备保序重试。Redis 使用事件 ID 原子去重及计数；小时数据完整时迟到事件以带版本的标记触发 MySQL 重归档，缺失或超保留期则隔离等待人工对账，`GET /api/events/archive-status` 可查看。当前补偿要求单后端归档调度器，不支持多个归档进程并发写同一小时；不能证明修复前小时数据完整，隔离数据尚无自动解封。Compose 添加独立持久卷，Redis 配置 `appendfsync always` 和 `noeviction`。变更部署前应确认磁盘和 Redis 持久卷、容量及写入性能，不能删除或重建已有队列；Redis 去重记录不自动过期，需监控内存与持久化状态。进程在事件写入 SQLite 前突然终止、存储长期不可用或 Redis 数据及队列同时损坏时，仍不能保证事件不丢失。

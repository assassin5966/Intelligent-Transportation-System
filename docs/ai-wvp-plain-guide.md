# 第一部分：配置原理（小白版）

## 一、整个事情在干嘛

摄像头（IPC）不是直接给你一个网址就能看的。它是个"国标设备"，说话走一套叫 GB28181 的规矩——你得先**喊它开播**，它才把画面推过来，而且推过来的是一包包的原始数据（RTP），不是浏览器/cv2 能直接看的格式。

所以中间需要两个"中间人"帮你搞定这件事。

## 二、两个中间人：WVP 和 ZLM

用**直播间**来类比：

```
摄像头(摄像师)  ──►  WVP(导播/调度员)  ──►  ZLM(直播间)  ──►  你(AI)
   拍画面            喊摄像师开播            把画面转成你能看的格式     拉流看
```

| 中间人 | 类比 | 干的活 |
|--------|------|--------|
| **WVP** | 导播/调度员 | 用对讲机（SIP）喊摄像头"开播"，管设备列表、谁在线 |
| **ZLM** | 直播间 | 收摄像头推来的原始画面包，**转成你能直接看的格式**（HTTP-FLV）|

> 你（AI）**不跟摄像头直接说话**，也不收原始数据包。你只跟"导播"（WVP）说一声，导播让摄像师开播、让直播间转格式，然后**给你一个直播链接**，你点开就能看。

## 三、IP 和端口 = 地址和门牌号

把网络想成一栋大楼：

- **IP** = 大楼地址（`192.168.1.200` 这栋楼在哪条街）
- **端口** = 门牌号（这栋楼的 `80` 号房间）

你要找一个人，得知道**地址 + 门牌号**两个才行，光知道地址不知道哪个房间，找不到人。

本项目要连两个"人"，所以需要两组 IP+端口：

| 找谁 | 地址(IP) | 门牌号(端口) | 干嘛 |
|------|---------|-------------|------|
| 导播 WVP（调度员）| WVP 那台机器 | `18080` | 跟他说"我要看1号摄像头" |
| 直播间 ZLM | ZLM 那台机器 | `80` | 点开他给的链接看画面 |

## 四、play/start = 找导播要直播链接

你不用自己猜直播链接是什么。你只要跟导播（WVP）说一句：

> "给我看 `设备ID`/`通道ID` 那路"

导播就帮你完成：喊摄像师开播 → 直播间转格式 → 然后**递给你一张纸条**，上面写着完整的直播链接：

```
http://192.168.1.200:80/flv?app=live&stream=摄像头ID_通道ID
```

这张纸条（`data.flv`）上，**地址、门牌号、频道全写好了**。你照着点开就行，不用自己拼。

这就是"**自动返回**"——导播算好了直接给你，不用你操心链接怎么拼。

## 五、为什么端口要"两边一致"

这里是最容易踩坑的地方。直播间的门牌号，**有两个地方会写**：

```
ZLM 自己的登记本(config.ini):      "我的直播窗口是 80 号"
WVP 导播的通讯录(application.yml): "直播间在 80 号窗口"
```

**这两处必须写一样的**。为什么？

- ZLM 实际在 `80` 号窗口发直播（它按自己的登记本开门）
- WVP 给你纸条时，按它通讯录上记的窗口号写
- 如果 ZLM 实际开了 `8088`，但 WVP 通讯录还写着 `80` → WVP 给你的纸条写 `80` → 你去 `80` 号窗口，扑空了

所以 **80 被占用要改的时候，两处登记本 + 大楼门牌（docker映射）必须一起改成同一个号**。只改一个就串了。

**但对你（本项目）来说**：你不用管这个号是多少——导播纸条上写几号你就去几号，照着走就行。所以本项目配置里**没有端口这一项**。

## 六、`.env` 里那些配置，逐个说人话

```bash
WVP_ENABLED=true
```
> "我要用导播，别让我自己手动找链接了"

```bash
WVP_API_URL=http://<导播地址>:18080
```
> "导播在哪栋楼哪个房间——这是你唯一要问部署方要的地址"

```bash
WVP_USERNAME=admin
WVP_PASSWORD=admin
```
> "进导播办公室要刷工牌，账号密码就是你的工牌"

```bash
WVP_SYNC_INTERVAL=30
```
> "每 30 秒问一次导播：有没有新摄像头上线？有没有掉线的？"

```bash
WVP_PLAY_PROTOCOL=flv
```
> "我要看 FLV 格式的直播（cv2 拉这个最稳），别给我 RTSP"

```bash
WVP_STREAM_SUB=true
```
> "给我看标清子码流就行，高清太吃推理算力"

## 七、为什么不用配 SIP ID / mediaServerId / secret

因为这些是**中间人之间的内部对讲机频道**：

| 不用配的 | 是什么 | 类比 |
|---------|--------|------|
| SIP ID / domain | 摄像头和导播之间的"工号" | 你点外卖不用知道骑手工号 |
| SIP 密码 `Gb@202608` | 对讲机加密密码 | 骑手之间通话加密，跟你无关 |
| mediaServerId / secret | 导播和直播间之间的认证暗号 | 后厨和前台的内部对接，顾客不参与 |
| SIP 端口 5060 / RTP 30000-30500 | 对讲机频道 / 传菜传送带 | 内部物流，你不走这条路 |

你作为**消费者**，只走"找导播要链接 → 点开链接看"这条路（REST API + HTTP-FLV）。中间人之间怎么对讲、怎么传菜，是他们内部的事。

## 八、一句话总结

**你只需要知道导播（WVP）在哪个地址（`WVP_API_URL`）、账号密码多少**。剩下的：喊谁开播、链接怎么拼、端口是多少、摄像头叫什么 ID——导播全帮你搞定，自动塞给你。你拿着链接拉流推理就行。

# 第二部分：AI 拉流链路详解（通俗版）

## 一、全景：AI 在干什么

想象一个保安坐在监控室，盯着屏幕，任务是"数有多少车/人过了这条线"。AI 干的就是这个事，只是 7×24 不眨眼：

```
接上监控信号 → 一帧帧看画面 → 认出车和人 → 记住每辆别认重 → 过线就+1 → 记账上报
   拉流         拆帧           YOLO检测      BoT-SORT跟踪     越线计数      事件推送
```

## 二、第一步：拉流 = 把监控信号接上，拆成一帧帧画面

监控给的是**连续的视频流**（像水管一直在流水），但 AI 一次只能"看"一张静止画面（一帧）。所以要有个"拆帧机"。

代码里这个拆帧机就是 `cv2.VideoCapture`（[stream.py:35](file:///Users/bianwei/Desktop/codes/DT/app/ai/stream.py#L35)）：

```
FLV视频流（水管） ──拆帧机──▶ 第1帧、第2帧、第3帧...（一张张图片）
```

- FLV 是个"包装盒"，里面装着 H.264 压缩的画面
- 拆帧机干两件事：拆开包装盒（解 FLV）→ 解压画面（解 H.264）→ 吐出一张张 BGR 图片
- 这活儿是**慢活**（要等 FFmpeg 解码），所以丢到后台线程干（`asyncio.to_thread`），**不堵住主线程**——主线程可以同时去发事件、推 WebSocket

> 类比：保安的监控屏接上信号，画面一帧帧刷新。屏幕刷新的时候，保安脑子还能同时干别的（记数、喊人）。

## 三、第二步：检测 = 一眼认出画面里有啥

拿到一帧画面，AI 要知道里面有**几辆车、几个人、在哪**。这是 YOLO 干的（[pipeline.py](file:///Users/bianwei/Desktop/codes/DT/app/ai/pipeline.py)）：

```
一张画面 ──YOLO──▶ "左上有辆车(置信度0.92)、中间有个人(0.85)、右边有辆卡车(0.78)"
```

- YOLO 是个"质检员"，一眼扫过画面，框出所有目标
- 每个框带：**类别**（车/人）+ **位置**（坐标框）+ **置信度**（多确定，0-1）
- 置信度低于 0.4 的丢掉（`YOLO_CONF`），别把树叶当车

> 类比：保安看一眼画面，"哦，这辆是轿车，那是个人，那辆是货车"。

## 四、第三步：跟踪 = 给每个目标发编号牌，别认重

**这是最关键的一步**。光检测有个大问题：

> 第 10 帧画面里有辆车在左边，第 11 帧这辆车挪到中间了——YOLO 只会说"有一辆车"，但它**不知道这俩是同一辆**。

如果不解决，同一辆车从左开到右，每帧都被当成"新车"，计数会爆炸。所以需要跟踪器 BoT-SORT（[tracker.py](file:///Users/bianwei/Desktop/codes/DT/app/ai/tracker.py)）：

```
第10帧: 检测到车A(左边)      → 发编号牌 #7
第11帧: 检测到车(中间)       → "这位置和#7上一帧很近，是同一辆" → 还是#7
第12帧: 检测到车(右边)       → 还是#7
```

- 给每个目标发个**编号牌**（track_id），盯住它一路走
- 记住它的**轨迹历史**（走过哪些点），后面计数要用
- BoT-SORT 比 ByteTrack 强在：车被挡一下、挨近一下，**不容易换编号**（ID 切换），不会把一辆车数成两辆

> 类比：保安给进场的每辆车发个号牌，"7号车从左开到右"，全程盯的是同一个号牌，不会重复数。

## 五、第四步：越线计数 = 门口画条线，过了就按计数器

画面上画一条**计数线**（你注册设备时填的 `line_coords`）。目标从线这边走到那边，就算一次（[counter 逻辑在 pipeline 内](file:///Users/bianwei/Desktop/codes/DT/app/ai/pipeline.py)）：

```
        画面
  ┌─────────────────┐
  │                 │
  │  车#7 →→→→→→    │   ← 从外往里走 = Enter（进）
  │ ────计数线────  │
  │        ↓锚点    │   ← 锚点定哪边是"里"
  │                 │
  └─────────────────┘
```

- **计数线**：一条任意角度的线，目标跨过去就触发
- **锚点**（`anchor_coords`）：定"哪边是里"。从外往里跨 = `Enter`，从里往外跨 = `Exit`——方向是绝对的，不靠线的画法方向
- **一堆防抖**（这是项目的精华）：防止在线附近抖来抖去误计——滞回带、反向冷却、ID切换过滤、单向过滤等 7 层

> 类比：保安在门口地上画条线，车从外面开进来过线了按一下"进"，开出去过线了按一下"出"。锚点就是"告诉保安哪边算外面"。

## 六、第五步：上报 = 记账 + 广播

计到一次，AI 干两件事（[pipeline.py](file:///Users/bianwei/Desktop/codes/DT/app/ai/pipeline.py)）：

| 动作 | 类比 | 给谁 |
|------|------|------|
| `POST /api/events` | 记到账本上 | 后端（落 Redis，统计/告警用）|
| WebSocket 推送 | 喊一嗓子"7号车进来了！" | 前端大屏（实时看轨迹和计数）|

> 类比：保安按完计数器，在本子上记一笔"9:05 一辆车进"，同时对着对讲机喊"又进一辆"，大屏那边马上刷新数字。

## 七、第六步：信号断了怎么办 = 两级自救

监控信号会断（网络抖、摄像头重启、ZLM 重启）。AI 的自救分两级（[stream.py:58-91](file:///Users/bianwei/Desktop/codes/DT/app/ai/stream.py#L58-L91)）：

```
画面卡住/读不到了
  │
  ├─ 第一级: "可能只是网络抖一下"
  │          用同一个链接重试 5 次（间隔 2→4→8→16→30 秒，越来越慢）
  │          大多数临时断流这级就恢复了
  │          还不行 ↓
  │
  ├─ 第二级: "链接可能过期了，找导播要个新的"
  │          打电话给后端 → 后端找 WVP 重新 play/start → 拿到新 FLV 链接
  │          用新链接重新接监控
  │          （10 秒内只准打一次，别一断就疯狂打电话骚扰导播）
  │
  └─ 都不行: 放弃，等 30 秒后 wvp_sync 自动重新拉起
```

**`url_provider` 就是"找导播要新链接的电话号码"**：
- WVP 同步来的设备 → 有这个电话（`enable_url_refresh=True`），断了能自救
- 手填 `stream_url` 的设备 → 没电话（`url_provider=None`），断了就断了（离线视频处理本来就不需要自愈）

> 类比：保安的监控屏黑了，先拍两下电视机（重试）；还不行，打电话给机房"给我重新接一路信号"（换链接）；电话也没有的，就等下次巡检自动重连。

## 八、整条流水线串起来

```
WVP给的FLV链接
    │
    ▼
cv2拆帧机(后台线程) ──▶ 一帧帧画面
    │
    ▼
YOLO质检员 ──▶ "3辆车2个人，位置如下"
    │
    ▼
BoT-SORT发号员 ──▶ "#7车从左走到中，#8人站着没动"
    │
    ▼
越线计数员 ──▶ "#7过线了，Enter +1"
    │
    ├──▶ POST /api/events（记账）
    └──▶ WebSocket（广播给大屏）
    │
    信号断了？→ 重试5次 → 不行找导播换链接 → 继续
```

每一帧都跑一遍这个流水线（每秒约 15-25 帧），就实现了实时计数。
